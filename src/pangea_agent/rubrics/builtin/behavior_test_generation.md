# 业务行为用例生成

本方法只适用于 task 中 `analysis_profile=behavior-test-v1` 的任务。

## 交付目标

从冻结源码和任务资料中形成可执行测试用例，优先覆盖：

- 正常主干和有业务意义的配置、模式、输入及已有状态分支。
- 超时、中断、资源不足、协议失败等异常处理。
- 底层错误向公开返回、回调、状态或日志的传播、转换与恢复。
- 初始化、关闭、重试、再次调用以及失败后的清理和恢复。
- 冻结 Coverage 中真实匹配的零执行函数或分支结果。

用例不需要先建立 Risk。发现有证据的问题时保留问题事实和相关用例；不能为了生成用例而假设产品有缺陷。

## 源码理解

先确认受支持的业务入口、输入状态和调用顺序，再沿调用链核实错误产生点、最终返回或回调、资源清理及后续状态。当前实现和正确预期分开表达；正确预期来自接口约定、需求、任务明确约定或可证的行为条件，不能把当前错误实现抄成正确结果。

共享 `case`、helper 或 cleanup 必须结合真实前驱条件和持久状态判断。C/C++ 按真实求值、类型、宏和条件编译理解；Lua 按真实返回值、异常和清理理解。私有 helper 或直接修改内部变量不是业务测试入口。

写第一条用例前，先在当前 Agent 的工作中完成一份最小行为路径表：公开入口或自动触发点、
起始状态、实际调用顺序、终止返回/回调、资源归属，以及下一次操作会继承的字段。先交付正常
主干、主要业务选项、完整失败传播和失败后再次操作；这些完成后再补内部 helper 的独立分支。
未完成跨函数或跨次路径时，不得用大量局部 `if` 用例代替主流程覆盖。

复杂模块还必须做以下核对，但仍以业务行为表达用例：

- 从公开调用者向下确认调用方向，同时区分显式 API、连接/回调自动触发路径和传输层钩子；不能只凭函数名猜谁调用谁。
- 条件编译同时核对 feature-on 实现与 feature-off 的公开桩或替代入口，不能把“主体未编译”写成“API 不存在”。
- 边界预期引用实际执行的比较式，并区分前置协议校验、后续缓冲区上限和错误转换发生在哪一层。
- 故障注入点必须在源码或受支持测试设施中真实可构造；普通引用计数、复制或查表操作没有失败分支时，不得假设 OOM/NULL 返回。
- 异步超时、取消和正常完成分别确认资源由哪个回调或 cleanup 路径释放，不能把正常路径清理套到超时路径。
- 重试和跨次调用逐项核对事务开始时哪些字段被重置、哪些状态保留，并明确第二次调用对返回码、回调和外部状态的实际影响。
- 跨次调用还必须从第一次结果追到具体 adapter/transport 终态，再核对第二次公开调用实际命中的
  底层状态守卫、异步资源是否真的重新创建、宿主下一次 poll/callback 使用的指针是否有效。
  公开入口返回成功不能被直接当成新事务已经启动；底层初始化被短路时，要继续算出确定后果。
  旧业务 status 串味与底层生命周期错误分别检查，不能相互替代。
- 第一次失败到第二次调用之间默认继承源码自然终态。不得为使重试进入 happy path 而直接把
  内部 adapter/transport 改回 ready/running；只有受支持的公开恢复动作、宿主自动转换或任务
  明确允许的重建操作才能改变前置状态，并要在用例步骤中写明。
- 源码已经能确定的跨次结果必须写成确定结论。发现旧 `status`、错误码、回调上下文或事务字段未重置时，沿成功和失败终点算出第二次操作的实际返回/回调；不得写成“可能为旧值或新值”、不得以缺少真实设备为由留待确认，也不得把已证实的当前错误行为当成正确预期。
- 每个返回码、状态、回调参数和资源释放次数都要沿该用例真实执行路径逐句核对。callee 已经
  改变状态时使用 callee 的实际终态；资源调用次数按该路径上的真实调用点计数，不能凭
  “统一清理”或函数名推断。
- 跨次失败用例必须让第一次操作真实进入事务并在回调已注册后失败，再执行第二次操作；启动
  前同步返回失败只能证明“可以重新发起”，不能证明旧事务状态是否污染新事务。至少核对
  status/state/flags/callback context/transaction id 等实际存在且跨次保留的字段。
- 用例步骤只能通过公开 API、自动触发点或已证实的宿主调用约定执行。内部 poll/helper 可以
  作为观测和证据，不能额外调用一次已结束的内部 poll 来构造一个真实调用方不会执行的
  “重入”业务步骤；若任务明确要求这种健壮性检查，必须标成白盒/开发协助测试并写出当前
  实现的真实后果。
- 消息、提交、回调和释放次数按实际调用点逐个列举后再给总数；不把“不再提交的最后一次
  poll”计入命令数，也不把 `put(NULL)`、条件分支或描述性步骤自动算成一次有效业务操作。

## 用例正文

每条 `test_case` 用普通文本或 Markdown 写清；一条正文包含一组共享入口和准备条件的用例时，
可以使用 `test_case_group`：

- 标题、所测行为和受支持入口。
- 前置条件；需要故障注入或开发协助时说明要制造的条件。
- 操作步骤与对应预期结果。
- 预期依据、外部观测和清理/恢复。
- 冻结源码坐标；有真实 Coverage 时写匹配 ID 和目标结果。

能够共同验证且入口、准备、外部结果和恢复一致的行为可以合并。错误反馈、资源后果或后续状态不同的行为应分别说明。不要按每个 `if` 机械生成一条白盒用例，也不要用固定数量替代完整判断。
同一公开操作下仅校验字段不同、但最终错误、观测、清理和恢复相同的分支，应合并为一个参数化
用例或一张输入表，不逐字段复制完整步骤。私有 helper 只有在产生独立业务结果、真实 Coverage
明确指向它，或无法由主流程观察且任务确实要求白盒补测时才需要独立用例。Planning purpose
中的函数名和 context 文件仅用于导航，不自动成为逐函数用例清单；context 调用方用于证明
入口和传播，不扩大 owned source 范围。

250K 上下文的 Analysis 要给同一 worker 的可能 closure 留出约 70000 token；首轮读取和输出应在
约 145000 输入历史内完成主干、错误传播、再次操作和清理。相同最终结果的枚举放入紧凑参数表，
不逐项重复整套依据；预算接近目标时停止低优先级 helper 扩读，使用已保存证据完成一致性检查。

没有 Coverage 输入时正常生成业务用例，并明确没有覆盖率补测结论。没有真实设备、故障注入
或尚未执行，只影响执行状态，使用“未执行 / 未实测”说明，不等于语义 `unresolved`。只有
冻结 task 允许的源码和资料确实不足以确定入口、预期或观测时才保存 `unresolved`；能够通过
当前允许源码继续核对的事项必须先读源码，不能把“本轮尚未读取”写成资料不足。

## Reviewer

盲审先独立确认重要行为和预期依据，不读取首轮结果，也不预先声称首轮遗漏。Comparison 再核对必要用例遗漏、错误预期、不可执行触发或观测、错误清理以及 Coverage 对应错误；这些 finding 不以证明产品缺陷为前提。Comparison 必须优先检查首轮的 `unresolved`、`可能`、
`待确认`、计数和跨次状态结论：源码可回答却仍悬置、同一用例给出两个互斥终态、或把未实测
当成未知，都属于需要修正的具体问题。正确且已经表达的行为不重复改写。
