# 业务行为用例生成

适用于 `analysis_profile=behavior-test-v1`。交付主体是测试人员可执行的简短业务用例，
同时保留完整主责源码的行为对应、流程和证据。

## 先确定场景，再核实实现

1. 完整读取 task.inputs 中的冻结用户文档和示例，确定产品操作、环境与期望。
2. 在 allowed_paths 中找到这些操作的 CLI、RPC、应用或配置入口，核实命令参数及最终输出。
   context_files 是导航；owned_regions 才是主责范围。引用文件用于证明操作和预期。
3. 从头到尾读完 owned_regions，形成完整的行为范围，再开始写用例。先保存一条简短
   范围 note：按业务行为合并源码段，列“输入或触发条件、外部结果或执行缺口、源码依据”。
   文档已有场景和源码新增行为放在同一张表。连续校验、超时、取消、恢复和条件编译
   分别沿实际路径判断；成功路径经过某个 helper，不代表该 helper 的错误分支也被触发。
4. 对一个场景固定“操作前状态 → 本次操作 → 产品结果 → 清理后状态”，沿生产调用链核实。
   保存简短 test_case，共用命令只在一条操作 note 中保存；场景齐备后汇总模块 flow。
   同一产品操作的成功、拒绝和恢复使用流程的不同路径，路径关联已保存用例。
   用例先保留 flow_refs=[]；汇总流程时，在 paths.case_ids 填已保存的 case_id，报告据此
   链接到用例。这样按实际完成顺序建立关联，流程编号只在生成流程时确定。
5. 最后将范围 note 中的行为对应到实际保存的用例、variants 或具体执行缺口，形成 summary。
   对应以用例真实输入经过的路径为准。不同触发路径分别保存独立用例，即使外部错误相同。仅路径、操作、判据和恢复一致的
   数据取值变化可以使用 variants；正常与非法参数不能合并。

Planning 的说明是待完成的工作范围，具体行为仍由 Analysis 核实。需求预期、当前实现与
已证实缺陷分开记录；仅因源码存在某个分支，不能假设产品提供制造该分支的操作。

## 核实一次操作的实际结果

- **看用户最终收到什么。** 从最外层产品入口追到响应写入或完成回调。异步内部函数返回 0
  可能只表示受理成功；若 RPC 等待完成回调，测试预期采用该回调最终返回给用户的结果。
  日志、返回数组、布尔值和设备名使用实际输出，不由函数名或内部返回值推测。
- **写明配置何时改变。** 操作前使用旧值 A，修改时使用不同的新值 B；逐步核对每一侧的
  当前值。preconditions 是第一步执行前同时成立的状态快照；本次要做的配置改变只写在
  steps.action。前置已完成的连接不再重复创建，清理恢复所有本次改变的配置及创建的对象。
  若先用正常输入验证环境，验证结束后应清理该连接，再开始使用同一名称的异常测试。
- **沿真实终态继续。** 失败后的重试继承实际连接、资源和配置状态。只有真实恢复、重建
  或自动转换才能改变它们；先核对底层守卫、异步资源及回调，再确定第二次操作结果。
  不能把启动前被拒绝等同于事务已启动后失败。
- **让故障可制造。** 核实故障设施、触发条件和恢复方式。没有交付的报文篡改器、内部同步
  开关、内存故障桩等不能假定存在；保存具体触发缺口及源码处理依据。辅助接口用例同样
  需要实际的触发方法、可观察的执行时机和清理方法；“认证正在进行中”等内部状态本身
  只是待制造的条件。方法未确定时，在 summary 保留该分支依据及缺少的执行条件。
- **按路径核实边界。** 使用真实比较式、调用方向和条件编译替代实现；正常完成、超时、
  取消分别核对状态与资源归属。C/C++ 按求值、类型和宏理解，Lua 按返回值、异常和清理理解。
  引用 callee 的实际终态，资源次数按该路径的调用点核实；相似状态分别确认错误分支。
  连续校验按执行顺序逐项追踪：在格式检查处退出的输入不能覆盖后面的长度或校验和错误。
  后续检查需要能通过前面检查的独立输入；尚未准备该输入时，说明具体缺口。
- **区分计时范围。** 产品超时、重连间隔和实验观察窗口各自有起点和结束条件；采用真实
  完成条件，不按参数名称相加推断响应时限。源码已能回答的结果继续读完依据再下结论。

以上核实用于 Analysis 理解和源码依据。共用操作 note 面向执行人员，只保存准备环境、
命令和参数填写方式。产品响应写在对应用例的 expected 中，流程沿用该结果；共用命令的
注释只解释参数用途。内部实现推演仅在结论确实需要时单列证据。

## 短用例示例

示例用于学习写法，实际功能与预期需要当前任务的证据支持。

**正确密钥连接成功**

- 前置：目标要求认证，主机配置匹配密钥，本次连接和设备不存在。
- 操作：主机连接目标，查询连接和设备。
- 预期：连接成功，出现本次连接及连接命令返回的设备。
- 清理：断开本次连接，查询确认连接和设备移除。

**错误密钥被拒绝，修正后恢复**

- 前置：正确密钥已验证能连接并已断开，目标配置保持不变。
- 操作：使用格式合法但不匹配的密钥连接；确认失败后改回正确密钥重新连接。
- 预期：首次被拒绝且没有本次连接和设备；修正后连接和设备出现。
- 清理：断开本次连接，查询确认连接和设备移除。

**在线更新密钥**

- 前置：主机与目标均使用密钥 A，现有连接和设备可用；主机已注册不同的新密钥 B。
- 操作：目标改为 B；主机对现有连接提交 B；查询连接和设备。
- 预期：更新成功，原连接及对应设备仍可查询到。
- 清理：断开本次连接并确认移除，将目标密钥恢复为 A。

## 保存方式

使用当前工具直接提交 object 作为 body，每条用例保存一份。正文只展开前置、操作、预期、
清理；命令全文放在共用操作 note，source_evidence 保存已读的 repo_id:path:line 和符号名。
已经在步骤说明的观测
无需再次填写。保持下列展示字段，按实际依据填写关联与变体：

```json
{
  "format_version": "behavior-test-case-v1",
  "case_id": "TC-001",
  "title": "错误密钥连接被拒绝，修正后恢复",
  "purpose": "branch",
  "test_level": "business_blackbox",
  "entry": "共用操作：连接、查询连接和设备、断开连接",
  "preconditions": ["目标使用密钥 A；正确密钥已验证能连接并已断开；主机已注册格式合法但不匹配的密钥 B"],
  "steps": [
    {"action": "使用 B 连接并查询连接和设备", "expected": "连接被拒绝，本次连接和设备不存在"},
    {"action": "保持目标配置，改用 A 重新连接并查询", "expected": "连接成功，查询结果包含本次连接及连接命令返回的设备"}
  ],
  "external_observations": [],
  "cleanup": ["断开恢复后创建的连接，查询确认本次连接和设备移除"],
  "flow_refs": [],
  "coverage_refs": [],
  "risk_refs": [],
  "variants": [],
  "execution_status": "not_run",
  "source_evidence": ["当前任务已核实的 repo_id:path:line"]
}
```

purpose：普通主干、业务分支、异常和恢复为 `branch`；真实 Coverage 驱动为 `coverage`；
已确认问题的验证为 `risk`。用例无需先建立 Risk。正式风险关联用例；源码证实无法通过
支持的业务入口到达时，记录不可达依据。没有 Coverage 输入就不声称完成覆盖率补测。
参数变体采用现有报告字段，例如 `variants: [{"input": "摘要 sha256，DH 组 ffdhe2048",
"expected": "连接成功，查询可见本次连接和设备"}]`，每项写清实际输入与预期。
共用数据表已有完整输入时，变体直接引用数据编号；保留原始数据，解释其含义时核对实际
字节与解析顺序。查询预期说明要找到的对象及字段，采用查询接口自身的响应结构。

test_level 按实际操作及观测确定：

- `business_blackbox`：产品 CLI、RPC、服务、配置等正常入口，结果由产品外部观察。
- `interface_contract`：有证据的公开 API，检查接口承诺的返回或输出。
- `developer_assisted`：业务灰盒：从产品入口执行，允许在前置、执行中或清理阶段定点注入故障；
  桩点只制造条件，主要预期仍为产品行为。写清注入位置、时机、值/延迟、作用对象和撤销。
- `whitebox_support`：正式步骤操作私有 helper、内部对象、poll 或内部状态，属于辅助内容。

先交付业务场景。Coverage 指向内部 helper 时先沿真实调用链寻找业务触发方式；能由外部操作
或灰盒注入验证时必须优先这样设计。确实只能内部验证时保留白盒辅助，不能冒充主交付。公开 API 与产品入口各自保留真实层级。

## 模块流程和完整范围

流程图使用产品动作和外部状态，路径与用例的条件、结果保持一致；当前实现与正确预期
不一致时，在路径说明和关联风险中表达差异。从已保存用例的 action、expected 和 cleanup
提炼节点与连线：准备、提交操作、成功/拒绝、查询、恢复。每条 path 表达一条用例或同一
外部行为的明确变体。按操作前状态和产品入口区分流程，例如“无连接时 attach”和
“已有连接时 set_keys”分别组织；每条路径只保留一条可执行的操作顺序，互斥分支各自成路。
路径的响应沿用关联用例已核实的 expected；用例预期为 RPC 错误时，图中也写 RPC 错误。
每条连线对应已描述的实际操作，连接失败后的节点只清理该场景实际创建的资源。
同一入口且实际触发路径、外部操作顺序、判据和恢复均相同的参数变体共用一条路径，输入差别保留在用例中；例如不同错误
密钥均为“连接 → 被拒绝 → 确认无连接”，可以关联这条路径。带重连恢复的用例另有路径。
源码的协议消息状态不转写为这张产品流程图的节点。
每个 unit 的 flow 正文统一采用 behavior-flow-v1 object，固定字段为 format_version、flow_id、
title、description、nodes、edges、paths、source_evidence。下面是字段合同，示例内容仅作说明。
不要改为只有 trigger/entry_points/paths 的另一种外壳；入口表达为 kind=entry 的节点，
触发条件写在 edges.condition/paths.condition，paths.node_ids 按实际顺序引用 nodes.id。
保存前由当前 worker 核对字段和引用；发现自己写了另一种外壳，只替换该 flow 原记录，
保留已核实的业务内容和用例关联，不重做源码分析。Python 不补造节点或推断路径。
示例外壳如下：

```json
{
  "format_version": "behavior-flow-v1",
  "flow_id": "F-001",
  "title": "连接结果与各自清理",
  "description": "使用已有密钥的连接测试，以及本次新建文件密钥的异常测试",
  "nodes": [
    {"id": "connect", "kind": "entry", "label": "使用已有密钥连接"},
    {"id": "ok", "kind": "main", "label": "连接成功，查询本次连接和设备"},
    {"id": "detach", "kind": "exit", "label": "断开本次连接，查询确认移除"},
    {"id": "rejected", "kind": "exit", "label": "连接被拒，查询确认无本次连接和设备"},
    {"id": "register", "kind": "entry", "label": "将专用样本文件注册为本次测试密钥"},
    {"id": "file_connect", "kind": "main", "label": "使用本次测试密钥连接"},

  "edges": [
    {"source_step_key": "connect", "target_step_key": "ok", "condition": "密钥匹配"},

  ],
  "paths": [
    {"path_id": "P-01", "title": "连接成功", "condition": "使用已有匹配密钥", "node_ids": ["connect", "ok", "detach"], "explanation": "清理本次创建的连接", "case_ids": ["实际对应的成功用例编号"]},
    {"path_id": "P-02", "title": "连接拒绝", "condition": "使用已有不匹配密钥", "node_ids": ["connect", "rejected"], "explanation": "确认无本次连接和设备即结束", "case_ids": ["实际对应的拒绝用例编号"]},
    {"path_id": "P-03", "title": "文件内容异常", "condition": "本次注册的样本文件内容无效", "node_ids": ["register", "file_connect", "file_rejected", "remove_file"], "explanation": "清理本次注册和专用文件", "case_ids": ["实际对应的文件用例编号"]}
```

节点 kind 使用 `entry/main/branch/error/propagation/recovery/exit`，连线引用已有节点。
多参与者节点标明参与者，跨参与者连线写明实际等待或通知关系。内部状态推演作为源码依据，
不复制进测试人员的操作和主要预期。

最终 summary 对完整 owned 范围说明：正常主干、业务模式、异常产生和传播、清理与恢复、
条件编译替代行为、真实 Coverage 的对应处置。可以关联已有用例或具体 unresolved，
不能用完成文档样例代替完整范围分析。引用未读但允许读取的文件时先核实，不能当成缺失。
summary 使用简短 Markdown 索引，按以下顺序填写当前任务事实：

- 分析范围及行为对应：一张表，列“主责行为、本轮用例或具体缺口、已读源码位置”。包含
  业务模式、异常传播、清理恢复与条件编译；已有用例的步骤和响应直接用编号引用。
- Coverage 输入：本次实际提供的覆盖率数据及补测对应；未提供时写“本次未提供 Coverage 数据”。
- 待补执行条件：确实不足的每项写“分支行为、缺少的具体操作/观测、源码位置”。已由本轮
  用例或参数变体明确处理的条件直接引用该用例。
- 执行状态：本轮用例的实际执行情况。

仓库里的已有测试脚本是场景和操作依据；覆盖率结论使用本次冻结的 Coverage 数据。

尚未实际执行的用例使用 `not_run`；缺少实际设备本身不否定可由源码确认的预期。
真正不足的入口、故障设施、依据或观测单独说明；保留 Agent 原始结论，Python 不判断质量。

每批保存前只检查一次：测试人员能否执行，前后状态和预期是否一致，能否完成恢复。
结束前仅对具体疑点补读；已保存的错误由同一 worker 精确替换，保留其他有效内容。
首轮输入历史目标约 145000 token，为同一 worker 的定向修正保留约 70000；相同入口、触发路径、操作、
判据和恢复的参数变体共用一份用例。variants 的每个参数组合独立执行整条用例，包括
前置准备和清理；下一组合开始前上一条连接和配置已按 cleanup 处理。按业务结果组织，
而非按内部函数数量展开。

## Reviewer

盲审先独立确认重要行为和预期依据，不读取首轮结果，也不预先声称首轮遗漏。Comparison 再核对必要用例遗漏、错误预期、不可执行触发或观测、错误清理以及 Coverage 对应错误；这些 finding 不以证明产品缺陷为前提。Comparison 必须优先检查首轮的 `unresolved`、`可能`、
`待确认`、计数和跨次状态结论：源码可回答却仍悬置、同一用例给出两个互斥终态、或把未实测
当成未知，都属于需要修正的具体问题。正确且已经表达的行为不重复改写。

## 业务可实施性与 70% 交付目标

最终独立用例中，黑盒与可实施灰盒合计至少 70%；不是代码覆盖率，也不能靠复制成功用例、
改标签、移入附录或将白盒改名 note 凑比例。所有保留的正式与辅助用例均计入分母。

逐条以“业务入口 → 可制造条件 → 外部判据 → 恢复”设计。正文的前置、操作和预期面向
测试执行人员；函数、字段、行号与内部因果放 source_evidence。普通用例不写“某函数解析
成功”“结构体字段正确”“进入内部状态”。删掉函数名仍需补出真实动作和观测。
抓包、已提供的运维日志和资源指标可用于黑盒观察，但不能只写“无泄漏/正常/恢复成功”。
必须给出能执行的观察操作及有依据的判据；内部返回 0 不等于异步业务完成。

灰盒可以在步骤写函数或变量，用于精确定位注入，不要求后续逐个跟踪函数。需明确目标
连接/请求、调用阶段、注入值或延迟、次数/时间窗及撤销。延迟应落在目标超时计时区间内且
超过真实阈值；不能假定“3 秒延迟必然超时”。撤桩后验证业务恢复。

body 可附 execution_readiness=ready/needs_instrumentation/unknown，以及简短 readiness_reason。
ready 表示设计入口、触发设施和观测有依据，不代表实测通过，execution_status 仍为 not_run。
需要开发新增桩点但尚无设施时标 needs_instrumentation，保留灰盒设计但不计入可实施分子；
已有设施只因当前未连接设备而未实测，不应因此降级。不能虚构 CLI、调试开关或报文工具。

公开 C API 的函数验证不自动算业务黑盒；test_level 按实际操作边界选择。纯内部对象/返回
值验证保留 interface_contract/whitebox_support。未分类或执行条件不足保留在分母。
每条独立触发路径一个 test_case；避免 test_case_group 隐藏成员数量，同路径数据变体不重复
计数。summary 简述比例、白盒必要性和目标范围的重要缺口；即使比例达标也必须补关键路径。

首轮完成前优先转化有价值的白盒候选：查业务入口、外部故障触发、灰盒注入。确实无法
转化时如实保留辅助用例和原因，不为比例编造业务预期。已有代码证据和内部分析不丢弃。


## 随业务分析完成轻量风险识别

风险识别是本 profile 的分析责任，不是可省略的选项。在阅读本单元源码和设计业务用例时，
同时检查异常分支、资源释放、错误传播、状态一致性及恢复。复用已读源码，仅对具体疑点
补读调用链；不另做全量风险扫描、不要求六维逐项报告、不设风险数量目标。
正常拒绝非法输入不等于产品风险。有证据支持可能造成泄漏、挂死、错误响应或状态异常的
失效条件时，单独保存 kind=risk 的 body object：risk_id、title、trigger、system_result、
external_observation、exclusion_condition、source_evidence、linked_test_case_ids。
区分已证实行为、推测与未证实条件，不能将 Reviewer 对用例质量的 finding 当作产品缺陷。
优先关联已有用例；仅触发路径尚未覆盖时新增独立用例，不为风险重复生成相同用例。
没有发现有依据的风险时，在已有 summary 中简述实际检查范围及结论；不生成空风险、
不宣称未检查的内容安全。无法验证的具体疑点保留依据与待确认条件。

用例 body 必须采用本文件的 behavior-test-case-v1 object：preconditions、steps[{action,expected}]、
external_observations、cleanup、variants[{input,expected}]。不要改成 precondition/test_steps/step，
也不重复生成顶层 expected_results。每条记录保存完整用例；每步动作与对应预期成对。
