# 业务行为用例生成

本方法只适用于 task 中 `analysis_profile=behavior-test-v1` 的任务。

## 交付目标

从冻结源码和任务资料中形成可执行测试用例，优先覆盖：

- 正常主干和有业务意义的配置、模式、输入及已有状态分支。
- 超时、中断、资源不足、协议失败等异常处理。
- 底层错误向公开返回、回调、状态或日志的传播、转换与恢复。
- 初始化、关闭、重试、再次调用以及失败后的清理和恢复。
- 冻结 Coverage 中真实匹配的零执行函数或分支结果。

用例不需要先建立 Risk。发现有证据的问题时保留问题事实和相关用例；不能为了生成用例而假设产品有缺陷。

正式交付先说明模块行为流程，再交付测试用例。源码函数、内部字段、回调和状态机用于核实流程；
测试人员的步骤与主要预期使用产品配置、连接、设备、IO、服务状态和日志等外部行为。

## 先确定测试目的

每条正式产品用例先声明一个主目的：

- `branch`：正常主干、业务选项、边界、异常传播、并发、重试或恢复行为。
- `coverage`：真实 Coverage 输入指出的函数或分支结果需要补测。
- `risk`：围绕已确认风险的触发条件和用户后果进行验证。

同一用例兼有多个目的时只保留一份正文，选择最直接的主目的，并通过 `flow_refs`、
`coverage_refs` 和 `risk_refs` 关联其他依据。没有 Coverage 输入时不得生成 `coverage` 用例。
主干基线属于 `branch`，不能因其没有分叉条件而省略。

## 先确定测试层级

同一个源码发现可以落到不同测试层级。写用例前必须先选择下列一层，不能把所有“可调用函数”
都称为业务黑盒：

- `business_blackbox`：测试人员从产品、服务、CLI、RPC、配置、连接、设备或自动触发入口操作，
  主要结果可以从产品外部观察。这是正式报告的首要交付。
- `interface_contract`：冻结证据只证明某个稳定公开 API 是受支持接口，测试动作就是调用该 API，
  Oracle 是公开返回值、输出参数或对外状态。它是合法接口测试，但不是产品级业务黑盒。
- `developer_assisted`：需要开发预先提供自动故障环境或观测设施；测试人员仍通过正常产品入口
  执行，主要结果仍是外部行为。开发协助只能出现在前置条件，不能成为测试步骤。
- `whitebox_support`：必须直接调用私有 helper、include 实现文件、修改内部字段、控制内部 poll、
  mock 单个内部调用或检查内部对象才能执行。它只能作为开发辅助附录，不得放进正式黑盒用例。

内部故障准备或人工环境复位若只出现在 `preconditions`/`cleanup`，正式步骤仍使用产品
入口，主要 Oracle 仍从外部判断，则整体归 `developer_assisted`。这种人工复位只是测试
环境清理，不能出现在正式步骤里，也不能说成产品恢复或自愈。只有必须在正式步骤中
改内部状态，或主要 Oracle 就是内部状态时，才归 `whitebox_support`。
以内部文件、内部对象或私有状态的出现作为并发/崩溃时机的同步信号，也属于内部测试设施：
应放在前置准备并归 `developer_assisted`。只有使用公开测试开关加外部定时，不读取内部工件，
且所有断言都来自产品输出时，才可保留 `business_blackbox`。

公开头文件或契约证明的 C/C++ API 可以形成 `interface_contract`；“公开 API”本身不自动升级为
`business_blackbox`。若冻结资料不足以找到产品入口，应如实交付接口测试或 `unresolved`，并写明
还缺哪个调用方、产品操作或外部 Oracle；不得用私有 helper 和逐函数用例填满业务黑盒区。

## 源码理解

先确认受支持的业务入口、输入状态和调用顺序，再沿调用链核实错误产生点、最终返回或回调、资源清理及后续状态。当前实现和正确预期分开表达；正确预期来自接口约定、需求、任务明确约定或可证的行为条件，不能把当前错误实现抄成正确结果。

共享 `case`、helper 或 cleanup 必须结合真实前驱条件和持久状态判断。C/C++ 按真实求值、类型、宏和条件编译理解；Lua 按真实返回值、异常和清理理解。私有 helper 或直接修改内部变量不是业务测试入口。

## 模块流程交付

每个模块先用一条或少量 `kind=flow` 记录说明主干、业务分支、异常传播、恢复，以及源码确实
涉及的并发关系。复杂模块可以拆图，简单模块不凑数量。`flow` 优先使用下面的软展示对象：

```json
{
  "format_version": "behavior-flow-v1",
  "flow_id": "F-001",
  "title": "测试人员能理解的模块流程标题",
  "description": "模块职责、入口和外部结果概述",
  "nodes": [
    {"id": "start", "kind": "entry", "label": "测试人员发起连接"},
    {"id": "done", "kind": "exit", "label": "连接成功且设备可用"}
  ],
  "edges": [{"source_step_key": "start", "target_step_key": "done", "condition": "认证成功"}],
  "paths": [{
    "path_id": "P-01",
    "title": "正确配置建立连接",
    "condition": "测试准备和分支条件",
    "node_ids": ["start", "done"],
    "explanation": "处理过程、外部结果、影响范围和恢复方式",
    "case_ids": ["TC-001"]
  }],
  "source_evidence": ["repo_id:path:line"]
}
```

节点 `kind` 使用 `entry/main/branch/error/propagation/recovery/exit`。每条边引用已声明的节点。
每条有测试意义的路径写清条件、结果、影响和恢复，并关联正式用例或具体待确认项。图描述源码
当前行为；正确预期与当前缺陷不一致时，在路径说明和风险用例中明确区分。
并发或多参与者流程的节点必须标明参与者；边只能连接该参与者的真实后继，或明确标注为等待、
通知、锁竞争等跨参与者同步关系。不得把 A 的完成节点写成 B 的执行结果或后继。

写第一条用例前，先在当前 Agent 的工作中完成一份最小行为路径表：公开入口或自动触发点、
起始状态、实际调用顺序、终止返回/回调、资源归属，以及下一次操作会继承的字段。先交付正常
主干、主要业务选项、完整失败传播和失败后再次操作；这些完成后再补内部 helper 的独立分支。
未完成跨函数或跨次路径时，不得用大量局部 `if` 用例代替主流程覆盖。

复杂模块还必须做以下核对，但仍以业务行为表达用例：

- 从公开调用者向下确认调用方向，同时区分显式 API、连接/回调自动触发路径和传输层钩子；不能只凭函数名猜谁调用谁。
- 条件编译同时核对 feature-on 实现与 feature-off 的公开桩或替代入口，不能把“主体未编译”写成“API 不存在”。
- 边界预期引用实际执行的比较式，并区分前置协议校验、后续缓冲区上限和错误转换发生在哪一层。
- 故障注入点必须在源码或受支持测试设施中真实可构造；普通引用计数、复制或查表操作没有失败分支时，不得假设 OOM/NULL 返回。
- 异步超时、取消和正常完成分别确认资源由哪个回调或 cleanup 路径释放，不能把正常路径清理套到超时路径。
- 重试和跨次调用逐项核对事务开始时哪些字段被重置、哪些状态保留，并明确第二次调用对返回码、回调和外部状态的实际影响。
- 跨次调用还必须从第一次结果追到具体 adapter/transport 终态，再核对第二次公开调用实际命中的
  底层状态守卫、异步资源是否真的重新创建、宿主下一次 poll/callback 使用的指针是否有效。
  公开入口返回成功不能被直接当成新事务已经启动；底层初始化被短路时，要继续算出确定后果。
  旧业务 status 串味与底层生命周期错误分别检查，不能相互替代。
- 第一次失败到第二次调用之间默认继承源码自然终态。不得为使重试进入 happy path 而直接把
  内部 adapter/transport 改回 ready/running；只有受支持的公开恢复动作、宿主自动转换或任务
  明确允许的重建操作才能改变前置状态，并要在用例步骤中写明。
- 如果结论是某个受支持的公开动作不能恢复，正式步骤必须在故障终态下实际执行该动作，并紧接
  一次公开重试或状态查询验证后果。不能只在流程说明或 note 中声称“无法恢复”。
- 源码已经能确定的跨次结果必须写成确定结论。发现旧 `status`、错误码、回调上下文或事务字段未重置时，沿成功和失败终点算出第二次操作的实际返回/回调；不得写成“可能为旧值或新值”、不得以缺少真实设备为由留待确认，也不得把已证实的当前错误行为当成正确预期。
- 每个返回码、状态、回调参数和资源释放次数都要沿该用例真实执行路径逐句核对。callee 已经
  改变状态时使用 callee 的实际终态；资源调用次数按该路径上的真实调用点计数，不能凭
  “统一清理”或函数名推断。
- 状态机中名称或结构相似的等待状态必须逐个核对其 `rc` 分支、状态更新和回调值。一个状态
  调用 `set_failure` 不代表相邻状态也会调用；不能把共同的“非 EAGAIN”条件概括成同一错误传播。
- 跨次失败用例必须让第一次操作真实进入事务并在回调已注册后失败，再执行第二次操作；启动
  前同步返回失败只能证明“可以重新发起”，不能证明旧事务状态是否污染新事务。至少核对
  status/state/flags/callback context/transaction id 等实际存在且跨次保留的字段。
- 用例步骤只能通过公开 API、自动触发点或已证实的宿主调用约定执行。内部 poll/helper 可以
  作为观测和证据，不能额外调用一次已结束的内部 poll 来构造一个真实调用方不会执行的
  “重入”业务步骤；若任务明确要求这种健壮性检查，必须标成白盒/开发协助测试并写出当前
  实现的真实后果。
- 消息、提交、回调和释放次数按实际调用点逐个列举后再给总数；不把“不再提交的最后一次
  poll”计入命令数，也不把 `put(NULL)`、条件分支或描述性步骤自动算成一次有效业务操作。

## 用例正文

每条 `test_case` 优先把 `body` 写成以下轻量 JSON object；这是便于客户端和报告稳定展示的软
交付格式。Python 原样保存，层级质量由 Reviewer 语义复核。旧任务和工具确实只支持字符串时，才回退为等价
Markdown。一个 record 对应一个共同入口、前置和恢复的场景，输入变体放在 `variants`，不要把
互不相关的函数清单塞入一个 `test_case_group`：

```json
{
  "format_version": "behavior-test-case-v1",
  "case_id": "TC-...",
  "title": "测试人员能理解的行为标题",
  "purpose": "branch | coverage | risk",
  "test_level": "business_blackbox | interface_contract | developer_assisted | whitebox_support",
  "entry": "产品操作入口或受支持接口",
  "preconditions": ["..."],
  "steps": [{"action": "测试人员动作", "expected": "该步外部结果"}],
  "external_observations": ["..."],
  "cleanup": ["..."],
  "flow_refs": [{"flow_id": "F-001", "path_id": "P-01"}],
  "coverage_refs": [],
  "risk_refs": [],
  "variants": [{"input": "...", "expected": "..."}],
  "execution_status": "not_run | executed | blocked",
  "source_evidence": ["repo_id:path:line"]
}
```

`format_version`、`case_id`、`title`、`purpose`、`test_level`、`entry`、`preconditions`、`steps`、
`external_observations`、`cleanup` 和 `execution_status` 是新用例应主动提供的展示信息；
`variants` 与 `source_evidence` 按实际情况填写。证据仍用于解释为什么这样测，不得进入测试人员
动作。层级由 Analysis 判断，Reviewer 独立复核；Python 只按 Agent 声明分区，不根据函数名、
关键词或内容猜测层级。

每条用例写清：

- 标题、所测行为和受支持入口。
- 前置条件；需要故障注入或开发协助时说明要制造的条件。
- 操作步骤与对应预期结果。
- 预期依据、外部观测和清理/恢复。
- 冻结源码坐标；有真实 Coverage 时写匹配 ID 和目标结果。

每完成一条内部行为链，立即把它转换成流程路径和测试人员用例后再保存。写入前只做一次交付
自查：不了解源码的测试人员能否完成步骤，主要预期能否从产品外部判断，故障准备和恢复是否
可执行。未通过时继续转换表达或保留具体缺口，不能把内部分析笔记作为正式产品用例提交。

能够共同验证且入口、准备、外部结果和恢复一致的行为可以合并。错误反馈、资源后果或后续状态不同的行为应分别说明。不要按每个 `if` 机械生成一条白盒用例，也不要用固定数量替代完整判断。
同一公开操作下仅校验字段不同、但最终错误、观测、清理和恢复相同的分支，应合并为一个参数化
用例或一张输入表，不逐字段复制完整步骤。私有 helper 只有在产生独立业务结果、真实 Coverage
明确指向它，或无法由主流程观察且任务确实要求白盒补测时才需要独立用例。Planning purpose
中的函数名和 context 文件仅用于导航，不自动成为逐函数用例清单；context 调用方用于证明
入口和传播，不扩大 owned source 范围。

250K 上下文的 Analysis 要给同一 worker 的可能 closure 留出约 70000 token；首轮读取和输出应在
约 145000 输入历史内完成主干、错误传播、再次操作和清理。相同最终结果的枚举放入紧凑参数表，
不逐项重复整套依据；预算接近目标时停止低优先级 helper 扩读，使用已保存证据完成一致性检查。

没有 Coverage 输入时正常生成业务用例，并明确没有覆盖率补测结论。没有真实设备、故障注入
或尚未执行，只影响执行状态，使用“未执行 / 未实测”说明，不等于语义 `unresolved`。只有
冻结 task 允许的源码和资料确实不足以确定入口、预期或观测时才保存 `unresolved`；能够通过
当前允许源码继续核对的事项必须先读源码，不能把“本轮尚未读取”写成资料不足。

## Reviewer

盲审先独立确认重要行为和预期依据，不读取首轮结果，也不预先声称首轮遗漏。Comparison 再核对必要用例遗漏、错误预期、不可执行触发或观测、错误清理以及 Coverage 对应错误；这些 finding 不以证明产品缺陷为前提。Comparison 必须优先检查首轮的 `unresolved`、`可能`、
`待确认`、计数和跨次状态结论：源码可回答却仍悬置、同一用例给出两个互斥终态、或把未实测
当成未知，都属于需要修正的具体问题。正确且已经表达的行为不重复改写。
