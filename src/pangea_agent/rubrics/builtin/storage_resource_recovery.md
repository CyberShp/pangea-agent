# 资源与恢复专项分析方法

## 适用条件

本方法是跨协议补充，只在冻结源码或当前资料中存在资源额度、对象池、引用计数、队列、缓存、句柄、
定时器、注册项、异步任务或明确恢复流程时采用。不能因为模块是存储或高性能组件，就假设存在泄漏、
耗尽或长稳风险。

资源语义以目标源码为准。SPDK、DPDK、内核或 SDK 中相似资源的回收方式只能提示检查方向，不能替代
当前资源的所有权、失败返回和销毁契约。

## 建立资源账本

对每类关键资源记录：

- 创建入口、容量来源、申请单位和失败返回。
- 所有者、借用者、引用增加/减少点，以及同步或异步释放条件。
- 全局、per-thread/per-core、per-session、per-queue 或 per-device 的作用域。
- pool、local cache、in-flight、completion、待回收和已释放等可区分状态。
- 初始化、正常停止、异常退出、重试、重连、reset 和进程重启各自的回收路径。
- 外部可观测量：新连接/请求能否进入、管理计数、内存/句柄、设备状态、吞吐和恢复时间。

## 分析步骤

1. 从业务入口沿真实调用序列列出每次 acquire/create/register/enqueue/increment，以及对应的
   release/destroy/unregister/dequeue/decrement；不要仅按函数名做静态配对。
2. 对多步初始化，在每个可能失败的步骤建立故障窗口。记录失败前已经成功的资源、错误传播、清理顺序、
   清理自身失败的处理和最终仍可达的所有者。
3. 区分“没有申请”“申请失败”“申请成功后部分提交”“进入异步执行”“完成待消费”和“已回收”。
   同一个错误返回在这些阶段的资源后果不同，不得合并。
4. 对 pool、ring、queue、descriptor、request、buffer 和连接额度，按真实比较式确认边界、保留项、
   per-core cache 和并发占用。总量减去空闲量不一定等于正在业务使用量。
5. 对引用计数建立对象级账本：哪一步获得哪一个引用、是否转移所有权、失败分支是否仍持有、异步回调
   最终减少哪个对象。相邻的增减函数不能代替同一对象、同一序列的证明。
6. 对资源耗尽重放三个阶段：达到边界前、首次失败、释放部分资源后再次申请。既要核对失败请求的状态，
   也要确认既有业务不被破坏和新业务恢复。
7. 对停止/异常退出，先停止新的提交，再处理在途任务和 completion，最后按依赖逆序释放。若代码改变
   顺序，必须证明依赖对象在最后一次使用时仍有效。
8. 对重试、重连和 reset，确认旧资源是复用、重置还是重建；旧 generation 的回调、完成或定时器不得
   被新对象接收。只清状态位但未恢复额度或服务能力不算恢复完成。
9. 长稳分析使用可重复的真实业务周期，例如连接/断开、创建/删除、失败/恢复或负载升降。每轮比较同一
   基线，并在最后执行一次新的业务操作；单次进程 RSS 上升不足以证明泄漏。

## 风险判定

- 只有完整序列能证明资源不可回收、额度持续下降、重复释放、悬空使用、既有业务受损或移除故障后仍
  无法恢复时，才形成 RiskCard。
- 到达容量边界后返回明确错误、保持既有状态且释放后可再次申请，是正确的资源保护，不是风险。
- “可能泄漏”必须落到具体资源、所有者丢失点和持续存活条件；GC、进程退出或外部组件自动清理是否
  生效必须按当前契约扣除。
- 仅有不对称调用、计数差或清理日志不足以证明系统后果。无法确认异步 runtime、内核或设备回收语义时
  保留 `UNRESOLVED`，写明需要的完成事件、外部契约或运行证据。
- 性能下降必须与资源状态建立因果，例如 cache 跨 NUMA、队列长期接近耗尽或重试放大；不能把压力下
  的普通抖动直接命名为资源风险。

## 转换为测试

- 用例先建立稳定基线，再制造一次确定的失败或耗尽条件，记录失败时外部结果，移除条件并验证恢复。
- 故障注入只控制第 N 次申请、提交或完成的失败，不预先制造泄漏或错误终态。
- 边界值来自源码/配置：至少覆盖边界前、边界和首次越界；不使用“很多连接”“长时间”作为唯一条件。
- 资源回到基线应同时使用直接计数和业务再使用证明；没有可靠计数时，至少验证同规模资源可以重新建立
  且真实 IO/业务成功，并将观测限制写清。
- 异常退出、优雅停止和服务重启的回收能力不同，分别生成用例。对象已失效后不继续用旧句柄观测。
- 长稳用例固定周期、负载、采样点和允许波动，并保留最后一次恢复操作；阈值必须来自现行规格、基线或
  可解释的容量关系。
