# 分支分析：业务行为覆盖（behavior-branch-v1）

用于当前 Run 冻结的分支场景。目标是发现业务条件、配置、状态、操作顺序与结果的差异，并形成可执行用例；不是一条 if 一条用例，不用语法分支数做质量分母。
不开展正式风险扫描，不建立 risk/check 风险账本，不要求 risk_refs，不判断实现“安全”或“存在缺陷”。参数拒绝、协商失败、超时和取消均可作为预期业务行为。需求/设计与实现不一致时分别保留预期来源、当前行为和待确认事项，不把正常拒绝升级成产品风险。

## 在本轮分析内发现覆盖项

先按 scene_flow 保存业务流程；它是可更新的理解草图，不是穷尽候选的边界。然后在同一 analysis 内执行以下工作，不新增 Agent、全局阶段或复核轮次。

1. **从证据提炼变化维度。** 对本单元负责的业务操作，追踪入口输入、可选配置、枚举/能力表、状态读写、事件顺序和外部结果；读取决定这些值的生产者、转换、使用者及必要直接依赖。类型与常量表是发现线索，不能仅列函数名或将全部内部变量机械变成测试维度。分别记录需求/设计允许的行为与源码实现的行为。
2. **找影响行为的关系。** 核实条件之间的约束、参数到消费者的传递、前驱状态与持久状态、操作的生效时机、超时/取消/完成的顺序，以及资源创建/使用/清理对再次操作的影响。沿真实调用链追到外部最终响应或冻结边界；异步受理不等于完成。跨单元关系按 purpose 明确的 owner 处理，引用 context 证据，不假设别人已覆盖。
3. **按适用方法推导候选。** 从下表选择能解释实际关系的方法，不要求每个单元凑齐全部方法，也不展开无关目录。

| 方法 | 使用条件与交付依据 |
| --- | --- |
| 等价类与有限选择 | 对产品支持的有限功能选项，每个有业务意义的合法值至少有用例/变体或明确不适用依据。整数、字符串、数量等大域按真实行为分区；机器类型有限不等于逐值穷举。非法、缺省、未配置等只有在证据支持相应行为时纳入。 |
| 边界值 | 由实际比较式、类型、转换及调用方限制推导边界，覆盖边界两侧与端点；先通过前面的校验，才能触发后面的边界。 |
| 决策表与受约束组合 | 多个条件共同决定行为时列有效规则与结果；核实不可能组合。单项取值覆盖不代替组合覆盖。小而有实际意义的有效组合可全列；组合较大时说明代表组合及未覆盖部分，pairwise 仅作补充，不能替代源码已出现的三因素或更高阶规则。 |
| 状态转换 | 由真实入口、前驱状态、守卫、动作和后继状态形成覆盖项；相同调用在不同状态下的结果分别核实。 |
| 场景序列 | 对重试、重新配置、取消、完成、清理及再次操作，保留影响结果的历史和顺序。按已发现的状态/数据依赖选择有限序列，不声称穷举无限历史或所有并发交错。 |

4. **核实归类与合并。** 对“两个输入等价”“此条件已覆盖”“恢复后可再次执行”等分析假设，尝试改变一个相关取值、前驱状态或事件顺序，看是否改变操作、结果或恢复。此处反例用于检查测试归类，不用于产品风险判定。共享函数、相同流程节点或相同错误码不证明业务等价；有差异则拆分。缺证据则保留具体未知，不自造支持能力、CLI 或注入设施。
5. **将候选逐项落实。** 不同触发路径、操作顺序、判据或恢复分别保存独立 test_case；仅这些要素均相同的数据取值可以放 variants，保留每项实际输入与预期。每个组合独立执行整条用例及清理。可为变体提供稳定 variant_id（如 V-01），供覆盖项准确引用；旧变体没有该字段时不得靠数组序号猜身份。purpose 通常为 branch。execution_readiness 与缺口按 scene_common_generation 填写，不因缺设施删掉重要行为。
6. **反向查漏。** 从已识别的业务维度、有效规则、状态与顺序回查用例/变体；再从用例回查实际触发条件和依据。补齐已知遗漏，更新同一逻辑流程与覆盖 note；不能用“已有成功/失败两条”证明所有配置和状态均已设计。

需求与设计提供正确预期，示例只参考操作和环境，历史缺陷与用户方法论补充边界/顺序经验并核实当前适用性。真实 Coverage 仅辅助排序及显式关联，本场景不承担全量代码 Coverage 补测。

## 业务覆盖记录：已有 kind=note，不新增写入门禁

每个分析单元维护一份 kind=note，body 约定 format_version=behavior-coverage-v1。它是 Agent 的分析记录与报告展示约定，不是 record_contracts，也不是 Python 对完整性、正确性或完成状态的判断。格式异常、旧格式、缺项保留原文和提示；由原 worker/Reviewer 核实，不拒写、不自动补造内容。

一项代表一个有业务意义的条件/配置/状态/顺序及预期，不按函数、语句或所有内部变量制造清单。item_id 在本单元内稳定，case_refs 指向本单元的实际用例；跨单元关系在 scope/reason 中明确 owner 和证据。scope、combination_strategy、operation、expected_behavior、reason 为字符串；conditions、constraints、source_evidence、unresolved_dependencies 为字符串数组；items 与 case_refs 为对象数组。可选 flow_refs 引用实际流程/路径，不要求猜造。

- designed：已有对应设计，case_refs 指向真实 case_id；有 variant_id 时精确引用。仅表示已设计，不表示可执行、已执行、通过或实测代码覆盖。
- missing：已确认重要业务行为与预期，但尚未生成对应设计；reason 写缺少什么。
- unresolved：行为、约束、预期或依赖尚不能核实；保留已知证据和所缺信息。
- not_applicable：有明确范围/约束依据证明该项不适用；不能把未读、未实现注入或预算不足当作不适用。

以下是假设源码示例，不能照搬功能或预期：

```json
{
  "format_version": "behavior-coverage-v1",
  "unit_id": "当前真实 unit_id",
  "scope": "本单元负责创建任务；持久化接口为直接参考，执行调度由另一明确 owner 负责",
  "combination_strategy": "支持策略逐项设计；数量按有效边界分区；只组合共同影响提交结果的条件，不声称全组合",
  "unresolved_dependencies": ["远端调度完成通知的冻结契约未提供"],
  "items": [
    {
      "item_id": "B-01",
      "operation": "提交任务",
      "conditions": ["任务不存在", "使用受支持策略 A", "数量为允许上限"],
      "constraints": ["输入先通过格式校验"],
      "expected_behavior": "提交被受理，查询可见本次任务；不将受理等同于执行完成",
      "source_evidence": ["示例仓库:src/task.c:20-48"],
      "case_refs": [{"case_id": "TC-001", "variant_id": "V-01"}],
      "status": "designed",
      "reason": "由创建入口与数量守卫推导，变体保留策略及数量"
    }
  ]
}
```

summary 说明已识别项的去向、组合/序列取舍及未知范围；计数用于导航，不是质量分数。不得宣称“找到所有未知遗漏”“100%业务覆盖”或把 variants 数量当作实测分支覆盖率。时间不足保留 missing/unresolved 及已有有效用例，不为清空缺口伪造设计。定向修正只更新受影响记录，保留稳定 item_id 和真实用例引用。
