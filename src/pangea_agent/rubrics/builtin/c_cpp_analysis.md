# C/C++ 源码分析方法

关注入口、调用链、状态机、错误路径、异步回调、销毁/恢复路径。

重点抽取：

- 外部入口、协议事件、CLI/REST 和状态机迁移。
- 资源所有权、申请/释放、引用计数、队列额度、预留与动态内存。
- 错误处理、清理、重试、取消、超时、初始化、卸载和复位。
- 共享状态、锁、原子、回调上下文和 C/C++ 边界。

错误行为已写入接口约定，只能证明“可能返回错误”，不能证明错误后的状态安全。若回调或底层实现可能先修改资源、链表、引用计数或句柄状态，再返回失败，必须继续检查部分副作用、调用方补救以及后续重试、关闭和恢复是否仍然可执行。为确认直接回调的副作用，可以读取 task 已提供的直接实现文件，但不得递归扩大范围。

遇到 `assert(false)` 后仍有清理或返回语句时，分别判断 Debug 与 Release：Debug 可能在到达清理前终止，不能用后面的清理代码证明该路径能够恢复。

实现注释描述“无法处理”、assert 某状态或假设某队列为空，只能说明实现依赖该状态，不能单独证明公开调用方已经承担了前置条件。只有公开接口契约明确规定，或入口代码在进入实现前实际检查并阻断，才能作为调用方保证。若 Release 构建移除断言后继续解除对象与容器的关联，必须继续核对未归还资源是否仍有可达的所有者和释放路径。

共享 helper、引用计数或公共状态被多个直接实现调用时，按实现分别检查进入条件、失败处理和退出状态。一个实现返回错误阻断后续操作，不代表另一个忽略错误继续执行的实现也安全；不同实现的结论不能合并成一个“不可达”或“未确认”。

状态断言与资源存在性相关时，检查完整时间顺序：状态可能在资源存在时置位，随后公开重配置、禁用或销毁资源却漏清状态，最后才在资源为空的分支触发断言。只证明当前分支不会新写入该状态，不能证明此前状态不会残留。

正常调用链梳理后，在源码范围和任务已提供的 C/C++ 直接实现、内联头文件中，单独从显式终止点、状态修改后的失败返回、被忽略或改写的关闭错误反向追触发条件。这个步骤用于发现高影响候选，不递归扩大文件范围，也不要求把每个普通错误返回都登记成风险。

输出必须先转成测试人员可制造的外部条件、可观测行为和恢复标准，再在证据中引用函数、变量和行号。
