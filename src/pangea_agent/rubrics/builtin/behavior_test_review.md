# 业务行为独立审查

适用于 analysis_profile=behavior-test-v1 的 Reviewer。读取 task.review_stage 区分以下工作。

## independent_review

本阶段交付审查依据，使用简洁的 Markdown summary/note；有具体疑点时保存 review_finding，
资料不足时保存 unresolved。完整用例和流程图由首轮 Analysis 交付。

独立阅读 owned 源码，按需要查阅冻结参考文件，形成紧凑行为表：入口/条件 → 实际返回、回调
或状态 → 清理和下一次操作 → 源码地址。覆盖正常主干、业务分支、异常传播、恢复、并发及
真实 Coverage 提示；相同外部结果合并表达。表格直接作为本阶段的审查记录，无需再展开为
一套逐条用例、步骤和流程图。不能读取首轮结果或预先声称首轮遗漏。

有疑点时沿调用链查到决定结果的具体语句。检查构建分支时，在冻结源码中查找同名入口的
各个定义及其条件；一个文件中未编译的实现不能证明整个构建没有此入口。区分生产替代实现
与测试 mock；结论必须符合实际定义、返回值和日志。没有读到的内容不等于不存在。

## comparison_review

复用上述独立审查依据，对照锁定的首轮结果。只为有实质差异的记录提交 finding，不重写
已经正确的交付。每项写明原结论、对应记录、具体源码反证、建议和未证实条件；新增缺项
可以没有原记录。多个不同问题分别说明证据如何支持各自建议，引用尽量定位到决定结果的
语句，避免用整文件引用代替核实。证据不足时记录待确认。

审查标准：

- 主干、业务分支、异常传播、清理恢复及有意义的并发行为有对应流程/用例或明确资料缺口。
- 逐个核对不同等待分支的返回码、状态和回调；同名/相似分支不能代替实际推演。
- 再次操作核对上次终态、底层守卫、新资源及后续回调，返回 0 不自动等于重试成功。
- 操作可执行，预期与外部观测一致；缺设备仅标未实测，不能据此否定源码可证明的结论。
- 层级真实：产品/CLI/RPC/连接等外部操作为 business_blackbox；直接调用公开 C API 为
  interface_contract；业务入口执行并以外部结果验收、允许定点故障注入的为 developer_assisted；
  私有 helper、内部字段、内部 poll 或单函数 mock 为 whitebox_support。不能仅凭标签放行。
- 用例包含前置、步骤、预期、观测及清理；同一结果的输入变化可用参数表，不机械要求每个
  helper 独立用例。冻结 Coverage 未提供则不能编造 coverage 用例；risk 用例关联已确认风险。
- 流程节点、边、路径说明和用例结论一致；跨参与者边须符合真实同步/因果关系。

给出基于证据的质量裁决；不能裁决时保持 UNRESOLVED。已完成的审查依据保持原文，
后续修正由原 Analysis worker 核实并完成。

## 整体业务用例比例复核

在现有 comparison 内核对全部有效用例，正文与开发辅助附录共同计数；以实际前置、触发、
观测、恢复判定，不能仅凭 test_level。抓包/运维日志不自动是白盒；注入步骤出现函数名不
自动是白盒；没有函数名但无法制造前置或只有内部判据的用例不能算合格黑盒。

至少 70% 是可实施黑盒+灰盒的交付目标。参数表不扩大数量，不同触发路径必须分开；未知
分类、纯内部 API、未具备注入设施的设计均不计入合格分子。对照正文逐条核实 readiness。
summary 明确分子、分母、比例及统计依据的用例编号，说明尚未转化的白盒和重要缺口。
对具体可转化的用例提出 finding（业务入口、制造方式或外部判据缺失/错误），交原 worker
定向修正；无需另派翻译 Agent。禁止为达标删掉重要白盒或增加重复成功用例。

低于 70% 或重要业务路径遗漏，质量裁决保持 UNRESOLVED 并列具体原因。Python 只汇总
声明，不裁决语义，不阻断结果提交。后续 closure 的新分类必须注明为原 worker 修正声明，
不能声称本 Reviewer 已复核未看到的新版本。无需再增加全量复核阶段。

target-first-v1 的主责范围以中性 unit_plan 的 owned_regions 为准。owned_scope_paths 仅为这些 region 所在文件，文件其余代码为参考。范围 note 说明依赖与排除项；复核 target 的真实遗漏，不恢复整目录全量分析义务。
