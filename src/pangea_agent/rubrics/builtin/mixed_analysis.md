# 多语言联合分析与边界复核

这是一个任务中的联合分析，按功能链路而非文件语言分割职责。以文件的 language 与实际源码为准，分别应用 C/C++、Lua、Python、sh/Bash 规则。一个单元可拥有多语言文件；跨单元依赖通过 context_files/context_regions 引用，主责不重复。

从用户入口追踪跨语言边界：Shell 启动 Python/C 程序、Python subprocess/FFI、C 进程调用/脚本嵌入、Lua host/模块绑定，以及共享文件和标准流协议。对每条与目标相关的关系记录两端源码证据、连接依据与未确认条件。构建映射、argv、解释器、cwd、env、退出码、stdout/stderr、编码、数据布局/所有权、超时/信号和清理行为按相关性检查。相同文件名、符号名或命令字符串本身不证明真实运行目标；动态目标、未冻结二进制和缺失构建/运行配置标为 UNRESOLVED 或待确认。

至少沿一条存在证据的目标业务链路检查正常路径及失败传播；没有可确认链路时如实说明，不编造。用例覆盖可外部触发的边界失败、清理恢复与可观测结果，例如下游非零退出后上游是否仍报成功、编码或参数分词是否改变输入。静态推断与实际执行证据分开。

调用图中的真实函数调用按调用点保留中间函数；进程启动到另一个程序入口是跨进程关系，不能伪装成同一进程中的直接函数调用。需要概括时在现有说明中明确省略层级，不能把传递调用写成直接调用，或把只检查部分输入的实现描述为完整校验。沿边核对实际 argv 与接收位置、解析结果、返回状态和持久化值，分别说明各层结果，避免用下游局部结论替代公开入口结论。

用例层级依据冻结需求/文档支持的正常产品入口，不依据文件能否直接运行。内部 Python 脚本有 `__main__`、C 后端可执行，均不自动说明它们是产品正常入口。为绕过上游缺陷而直调内部适配脚本或后端的探针可以保留为组件诊断/辅助证据，但不能标为 business_blackbox；只有存在公开接口承诺时才按 interface_contract 描述，否则沿 whitebox_support 保留真实边界。正式业务用例仍通过已确认的产品入口验证，分别记录契约预期与上游缺陷导致的实际表现；不靠绕过上游、改层级或删减有价值证据凑比例。

交付用例时重新核对最终写出的命令，而不只核对探针驱动：核对解释器选项与真实入口形式（脚本路径、-m 模块或 -c 命令等），不要重复插入脚本路径；明确源码目录与调用者 cwd，给含空格、空串、通配符或控制字符的参数保留字面值传递方式。共用操作可以复用，但具体步骤的路径、参数个数与引号必须与它一致。连续步骤继承前一步的文件和额度等状态；独立变体明确重置到哪一前置状态，不能把分别在全新目录执行的探针合并成连续步骤后仍照搬其预期。观测为“不存在”或“保持不变”时，说明调用前是否存在及比较基准。探针执行成功不自动证明转写后的用例可执行，契约预期与当前缺陷观测分别说明。

Reviewer 对照调用方与被调用方确认参数、返回值和副作用契约，不只分别审核各语言文件。复核跨单元边界是否有人负责、重复风险是否为同一因果链、未确认关系是否被误报为事实。无需另造结果格式或机械数量门禁；使用现有 flow、risk、test_case、summary、finding 和证据字段保存 Agent 原文。

在现有对照审核中逐步核对最终用例命令、前置状态及变体重置，并对照其引用的实际探针输入；两者不一致时不能仅以“已实测”放行。核对 business_blackbox 的命令是否真从需求支持的产品入口进入，不能因组件直调有实测结果而认可其业务层级。确认的错误指向原记录交原 Worker 定向修正，不由宿主代写结果，也不增加审核轮次。
