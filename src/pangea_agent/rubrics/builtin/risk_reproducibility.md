# 风险可复现四要素

风险必须回答：

1. 什么条件可以复现。
2. 系统出现什么结果。
3. 测试侧如何观察。
4. 改变什么条件可以排除。

风险是面向测试人员的“测试风险”，不是开发缺陷摘要。源码根因可以是白盒的，但 RiskCard 的用户可见主叙述必须先完成一次白盒到测试语义的翻译：

```text
内部失败条件 / 状态异常
→ 对应的受支持业务入口或运行场景
→ 测试人员可建立的触发条件
→ 系统级结果
→ 外部观测
```

因此：

- `title` 描述系统/业务风险，例如“已有连接在运行中切换配置后可能无法继续接收”，不得只写“引用计数失衡”“状态位未清”“xxx_release 断言”等实现现象。
- `trigger` 描述测试人员能够理解的真实场景、配置顺序、业务入口和必要故障条件。函数名、结构体字段、源码行号不得替代触发步骤；确实需要内部条件时，把“需要开发协助制造什么条件”作为灰盒前置语义，而不是让测试人员直接调用内部函数。
- `system_result` 描述服务、连接、IO、数据、资源可用性或恢复状态等系统结果，不把变量值、链表成员关系、引用计数值本身当成最终结果。
- `external_observation` 必须给出测试侧能判断 PASS/FAIL 的观测位置，例如业务返回、连接状态、服务进程、设备状态、管理接口、日志或指标；不能以“某字段仍为 true”“某函数被调用”作为主要 oracle。
- `exclusion_condition` 用测试/运行条件说明什么情况下该风险不成立；具体代码阻断点作为白盒证据下沉到 `upstream_semantics` 或 evidence。
- `exclusion_condition` 本来就应与风险触发条件相反。例如风险只在关闭失败时成立，那么“关闭成功时状态与返回值一致”是有效排除条件，不是语义颠倒。只有该条件满足后风险仍会发生，或它与冻结源码/现行规格矛盾时，才要求返工；同义改写和措辞澄清不构成正式返工。
- 函数名、变量名、引用计数、链表、assert、具体行号等实现细节放在 `affected_paths`、`upstream_semantics` 和 `evidence` 中，用于解释“为什么值得测”和定位根因，不占据风险主叙述。

一个快速判定标准：隐藏所有函数名、变量名、行号和内部结构后，测试人员仍应能理解该风险“什么场景、会坏成什么样、到哪里观察”。做不到时，这仍只是白盒 finding，不应作为最终 RiskCard 提交。

Sanitizer、函数名、变量名只能作为辅助证据，不能替代系统级 PASS/FAIL oracle。

`系统结果` 必须按真实执行顺序从证据推导：触发前状态 → 已发生的副作用 → 失败点 → 调用方处理 → 最终状态。公共对象绑定、实现层链表、内核轮询注册、请求队列和资源计数是不同状态，不得因为其中一个仍保留就声称另一个也仍有效。

冻结一条风险前，只选择一个 `trigger` 场景和一个终态，并为这条执行顺序列出返回值、错误原因、每项副作用的发生次数和最终状态。`title`、`system_result`、`external_observation`、`exclusion_condition` 只能陈述这一个场景；不得把“失败后立即继续使用”和“修正条件后重试成功”等不同时间点或终态混在同一张 RiskCard。标题中的“重复、丢失、阻塞、恢复”等词也必须与状态次数一致，不能只把正文写对。

`trigger` 必须列出形成起始状态所需的每一次状态改变操作，并使用能够复现风险的最短序列。正文若从
`count=1`、`committed=true` 等非初始值继续推导，trigger 中必须先有产生该值的调用；不得把未写出的
预热调用藏进 `system_result`。同一失败连续执行两次会改变注册数或计数时，只有风险本身需要“两次失败”
才这样写；普通“失败后修复并重试”只失败一次。

`trigger` 中使用“或”连接的每个替代条件都必须单独重放。它们到达同一失败点且风险相关的系统结果、
外部观测相同时可以合并，但必须逐项保留输入对应的精确内部值；失败点或风险结果不同则拆成不同风险，
或删除没有证据的替代条件，不能用一个分支的终态概括另一个分支。

状态向量必须逐字段来自同一条已重放的 failure path。failure path 的 `final_states` 要覆盖本路径
提到的每个计数器、布尔状态、集合成员、注册项和返回值，包括“未执行/未改变”的项；能确定次数
时写准确次数。RiskCard 不得新增 failure path 没有建立的计数、重复次数或终态，也不得把“某一类
callback 重复”扩大成“所有 callback 都重复”。需要新增字段但当前 checkpoint 没有证据时，保持
unresolved，不用概括词补齐。

对照资料与源码时先逐项写成同名状态：`executed/not executed`、`true/false/nil`、绝对次数和本次
增量，再判断是否冲突。资料写“第三步不执行”且源码也在第二步失败后立即返回时，两边同为
`not executed`，不得反说成“资料要求第三步执行”；相同布尔值、空值或次数也不得仅因句式不同判为
矛盾。只有同一字段的方向或数值确实不同，才形成风险或 review issue。

容器/注册表中的条目数量与条目执行后产生的业务字段值必须分开计算。先列出每个条目的函数体或
动作实际写哪些字段，再按当前路径的真实执行次数逐字段求和；不能把容器大小直接复制成计数器值。
测试资料给出的正确值与源码当前错误值也必须分开保存：RiskCard 写当前错误结果，TestCase 的
`steps[].expected_result` 写现行契约的正确结果，两者不同不构成自相矛盾。

残留标志只证明该字段未清理，不自动证明持续通知、持续阻塞、重复移除或容器破坏。若终态还依赖另一个计数器、容器成员关系、全局配置或对象配置，复现条件必须按顺序说明这些状态如何同时成立；任何中间操作已经清除所需状态时，应缩小或排除该终态。

如果路径包含关闭、销毁、注销或释放，最终状态必须扣除对象自身及外部组件自动完成的清理。声称注册、事件或引用仍存在时，要说明它为何没有随清理消失；只有重复句柄、并发已返回事件或延迟回调才能保留时，这些条件必须进入复现条件，不能藏在推测里。无法从冻结输入确认外部清理语义时，结论保持 unresolved。

复现条件中的边界值必须绑定真实比较式和失败哨兵。创建函数失败返回 -1 时，0 仍是有效候选；测试数值要明确落在目标分支一侧，不能用“较小”“一批”或“通常为正”替代。

`upstream_semantics.conclusion=expected_behavior` 表示该路径与当前规格一致，不是产品风险；不得继续保留 RiskCard。若仍需补测，使用需求、资料或 Coverage 关联生成非风险用例。

底层删除、注销或关闭返回失败时，必须结合具体失败条件判断操作对象是否仍存在。只写“返回失败”不构成完整复现条件；必须选定一个具体失败原因并推导对应最终状态。若该原因表示对象缺失、句柄失效或注册解除，除非明确重建资源，不得再推导为依靠原状态继续服务。若不同错误原因会产生不同最终状态，应缩小复现条件并分别写清；不能把某一层仍保留直接改写成另一层仍有效。依赖未定义调用方误用或不可达入口的结论不得作为产品风险。`外部观测` 必须来自推导后的最终状态，而不是来自预期设计。

缺失或无效配置本身不自动构成产品风险。只有当前资料/公开契约明确支持该输入，或明确要求入口对它
返回结构化失败时，异常传播方式才可形成 RiskCard/TestCase；资料只描述有效配置且没有规定无效输入
行为时，把该候选保留为不支持的调用方输入并排除，不能用“入口可调用”替代产品契约。

`historical-issues/<issue_id>.md` 是用户人工确认过的历史问题参考，不是当前代码缺陷证明，也不是现行
需求。它可以提示 worker 重点重放某个触发和恢复场景，但只有当前冻结源码仍能独立建立同一失败路径时
才能形成 RiskCard。RiskCard 一旦引用 `historical_issue` 资料证据，必须同时引用当前单元的 `code` 或
`source_context` 证据；只引用历史问题不得提交当前风险。当前源码不再支持该问题时，不保留 RiskCard，
可以在存在现行通过标准时生成资料驱动的回归用例。
