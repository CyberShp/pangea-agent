# 风险可复现四要素

风险必须回答：

1. 什么条件可以复现。
2. 系统出现什么结果。
3. 测试侧如何观察。
4. 改变什么条件可以排除。

风险是面向测试人员的“测试风险”，不是开发缺陷摘要。源码根因可以是白盒的，但 RiskCard 的用户可见主叙述必须先完成一次白盒到测试语义的翻译：

```text
内部失败条件 / 状态异常
→ 对应的受支持业务入口或运行场景
→ 测试人员可建立的触发条件
→ 系统级结果
→ 外部观测
```

因此：

- `title` 描述系统/业务风险，例如“已有连接在运行中切换配置后可能无法继续接收”，不得只写“引用计数失衡”“状态位未清”“xxx_release 断言”等实现现象。
- `trigger` 描述测试人员能够理解的真实场景、配置顺序、业务入口和必要故障条件。函数名、结构体字段、源码行号不得替代触发步骤；确实需要内部条件时，把“需要开发协助制造什么条件”作为灰盒前置语义，而不是让测试人员直接调用内部函数。
- `system_result` 描述服务、连接、IO、数据、资源可用性或恢复状态等系统结果，不把变量值、链表成员关系、引用计数值本身当成最终结果。
- `external_observation` 必须给出测试侧能判断 PASS/FAIL 的观测位置，例如业务返回、连接状态、服务进程、设备状态、管理接口、日志或指标；不能以“某字段仍为 true”“某函数被调用”作为主要 oracle。
- `exclusion_condition` 用测试/运行条件说明什么情况下该风险不成立；具体代码阻断点作为白盒证据下沉到 `upstream_semantics` 或 evidence。
- 函数名、变量名、引用计数、链表、assert、具体行号等实现细节放在 `affected_paths`、`upstream_semantics` 和 `evidence` 中，用于解释“为什么值得测”和定位根因，不占据风险主叙述。

一个快速判定标准：隐藏所有函数名、变量名、行号和内部结构后，测试人员仍应能理解该风险“什么场景、会坏成什么样、到哪里观察”。做不到时，这仍只是白盒 finding，不应作为最终 RiskCard 提交。

Sanitizer、函数名、变量名只能作为辅助证据，不能替代系统级 PASS/FAIL oracle。

`系统结果` 必须按真实执行顺序从证据推导：触发前状态 → 已发生的副作用 → 失败点 → 调用方处理 → 最终状态。公共对象绑定、实现层链表、内核轮询注册、请求队列和资源计数是不同状态，不得因为其中一个仍保留就声称另一个也仍有效。

冻结一条风险前，只选择一个 `trigger` 场景和一个终态，并为这条执行顺序列出返回值、错误原因、每项副作用的发生次数和最终状态。`title`、`system_result`、`external_observation`、`exclusion_condition` 只能陈述这一个场景；不得把“失败后立即继续使用”和“修正条件后重试成功”等不同时间点或终态混在同一张 RiskCard。标题中的“重复、丢失、阻塞、恢复”等词也必须与状态次数一致，不能只把正文写对。

残留标志只证明该字段未清理，不自动证明持续通知、持续阻塞、重复移除或容器破坏。若终态还依赖另一个计数器、容器成员关系、全局配置或对象配置，复现条件必须按顺序说明这些状态如何同时成立；任何中间操作已经清除所需状态时，应缩小或排除该终态。

如果路径包含关闭、销毁、注销或释放，最终状态必须扣除对象自身及外部组件自动完成的清理。声称注册、事件或引用仍存在时，要说明它为何没有随清理消失；只有重复句柄、并发已返回事件或延迟回调才能保留时，这些条件必须进入复现条件，不能藏在推测里。无法从冻结输入确认外部清理语义时，结论保持 unresolved。

复现条件中的边界值必须绑定真实比较式和失败哨兵。创建函数失败返回 -1 时，0 仍是有效候选；测试数值要明确落在目标分支一侧，不能用“较小”“一批”或“通常为正”替代。

底层删除、注销或关闭返回失败时，必须结合具体失败条件判断操作对象是否仍存在。只写“返回失败”不构成完整复现条件；必须选定一个具体失败原因并推导对应最终状态。若该原因表示对象缺失、句柄失效或注册解除，除非明确重建资源，不得再推导为依靠原状态继续服务。若不同错误原因会产生不同最终状态，应缩小复现条件并分别写清；不能把某一层仍保留直接改写成另一层仍有效。依赖未定义调用方误用或不可达入口的结论不得作为产品风险。`外部观测` 必须来自推导后的最终状态，而不是来自预期设计。
