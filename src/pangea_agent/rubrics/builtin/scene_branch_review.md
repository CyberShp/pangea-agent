# 分支业务行为复核（behavior-branch-v1）

仅当当前冻结分支场景包含本规则时执行。与 scene_branch、scene_common_review、scene_flow 一起使用；不因工作树规则更新给旧 Run 追加责任。本规则是必读场景方法，不依赖 Planning 是否选中可选方法论。

复核对象是业务条件、配置、状态、操作顺序、结果及恢复的测试覆盖，不开展产品风险判断，不要求 risk/check 风险账本或 risk_refs。正常拒绝与预期错误处理不是风险。review_finding 记录用例/流程/覆盖交付问题，不等于产品缺陷。

## 独立识别，再双向对照

- 标准型 independent_review：只读冻结源码、资料与中性单元职责，不读取首轮结果、历史流程基线或增量父记录。此处限制针对新冻结规则的独立盲审，不改变增量 Analysis 按合同参考父记录的职责。按业务入口独立提炼会改变行为的输入/配置、约束、状态、顺序和外部结果；核实必要的跨单元生产/消费关系。保存简洁 note，不重新生成整套用例，不盲目逐行展开。
- Comparison：沿用独立依据，对照锁定的首轮流程、behavior-coverage-v1 note 与用例/variants。速度型无独立盲审，在现有 comparison 内先按源码形成简短覆盖依据再核对已有产物，不声称完成盲审，不新增回合。
- 正向检查：每条用例/变体是否具有真实入口、可制造条件、前置约束、最终结果及恢复依据；相同返回码/共享 handler 不证明等价，不同触发、顺序或恢复不得混为一条。
- 反向检查：从独立识别的重要有限选择、边界、有效决策规则、状态转换及相关序列查到真实用例/变体或明确缺口。不只检查已经生成的内容；缺少某个重要覆盖项也可以提出 finding，即使原记录不存在。

## 判断依据

1. 有业务意义的受支持有限选择是否各有去向；大域是否依真实行为分区，合法与不合法条件是否混淆。不能拿一个成功样本证明所有选择。
2. 多条件共同决定结果时，组合约束和选择策略是否有依据；单项覆盖、pairwise 或同一条路径不能替代明确的高阶规则。边界输入是否真的通过前序校验到达目标判断。
3. 前驱状态、持久状态、配置生效时机和事件顺序是否影响结果；清理、取消或失败后再次操作是否继承真实状态。关系 owner 和参考证据是否明确，不能两边都假设对方已处理。
4. 覆盖 note 中 designed 是否指向实际 case_id/variant_id，且该输入实际触发所述行为。无稳定 variant_id 的旧数据按原输入核实，记录具体依据，不由宿主按数组位置猜测。missing/unresolved/not_applicable 是否与证据及原因相符。
5. 用例中的 readiness/execution_status 与覆盖 note 的 designed 分开：设计完成不证明可实施或实测通过。计数、图形可渲染及 note 格式完整不证明业务覆盖充分。
6. 流程身份、主路径和连线遵循 scene_flow。仅在 comparison 读取 task 明确提供的 flow_baseline、flow_comparison，检查实质变化及证据；允许发现并修正旧遗漏，不为保持图形相同隐藏新发现，不把未复核候选自动当作已验收基线。

发现有依据的遗漏、错误或不当合并，用现有 finding 指明操作/条件、源码依据、受影响记录及应补内容，交原 worker 一次定向修正。资料不足明确 unresolved，预算不足保留未完成范围。不得要求人为补齐不存在的功能、凑全部方法或生成全部笛卡尔积。

覆盖 note 使用已有 kind=note，仅由 Reviewer 判断其含义与缺口。缺失或格式异常不授权 Python 拒写、代补、改变 action/Run 状态或新增完整复核轮次；仍须保留正确内容及现有裁决流程。结论说明范围、组合/序列策略和剩余缺口，不保证不存在未知遗漏，不声称实测业务/代码覆盖达到 100%。
