# Lua 分析单元规划

根据 task 提供的 Lua 源码元数据、`require_dependencies`、状态写入、错误/coroutine 线索和资产候选，把请求范围划分为功能完整、工作量受控的分析单元。

优先按以下关系归并：

- 同一个 Lua module 或共同组成同一对外功能的文件；
- 模块入口与其直接 `require` 的仓库内实现；
- 共同读写同一 module table、对象字段、缓存或生命周期状态的文件；
- 同一 protected call 错误传播、恢复或 coroutine 状态流程；
- service/消息入口、注册动作与其业务处理实现；
- 设计资料明确归属于同一模块。

不要只按目录层级或文件名前缀拆分。请求源码只能归属一个单元；仅供其他单元理解的仓库内直接依赖放入 `context_scope`。外部、动态或候选不唯一的 require 保留为依赖边界，并在确实影响当前单元判断时写入 `unresolved`，不为凑齐源码而扩大冻结范围。测试文件和生成代码默认作为行为证据或上下文，只有它们本身属于目标功能实现时才取得源码所有权。

规划时确认每个单元同时覆盖入口、主要状态、异常/恢复和退出，不把一条完整生命周期拆成互相无法独立判断的小段。仍按 task 的行数、函数数和直接调用链预算控制单元大小；需要归并时优先保留功能完整性。

## target-first-v1 范围规则

task.scope_policy=target-first-v1 时，target 是分析对象，owned_scope_paths 是可选主责候选，
不是整目录交付义务。先按业务目标选 owned_files/owned_regions，再分单元；必要调用方、
CHAP 等耦合依赖放 context，其他功能不生成独立用例。同文件包含其他功能时允许按 region
划分，不受“整文件一个 unit”限制。以源码关系判断，不能只匹配 TLS 等名字。
用一条范围 note 写清主责、必要依赖和未纳入范围的功能及理由；未分配候选不是自动遗漏，
但不能漏掉 target 的真实业务路径。旧 task 未声明此 policy 时仍按其冻结范围执行。
