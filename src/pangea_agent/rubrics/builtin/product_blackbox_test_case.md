# 产品级黑盒用例转换

本规则是 PANGEA worker 在 tests 阶段固定读取的内置方法。它只负责把源码或协议层发现转换成
测试人员可执行的产品级用例，不增加分类、门禁、审计或返工流程。

```text
源码或协议触发条件
→ 测试环境中的产品状态
→ 测试人员使用的正常配置、连接、断开、重连、读写或重启操作
→ 测试人员可看到的连接、设备、IO、服务或日志结果
```

## 写法

- 步骤只写测试人员通过产品正常入口能完成的操作，并保留触发结论所需的最少动作。
- 函数名、字段、源码行号、内部状态和协议字段只留在风险证据中，不作为测试步骤或主要预期。
- 内部 callback、队列、对象释放或资源回收要转换成连接、IO、设备、服务或日志的外部结果。
- 需要内部故障条件时，只在前置条件中写明开发预先提供的自动故障环境、自动触发条件和恢复
  时机；测试人员仍从正常产品入口执行和观察。无法稳定制造时标为 `Developer-confirm`。
- 故障注入只制造触发条件，不能预先制造待验证的泄漏、崩溃、挂起或错误状态。
- 删除、注销或关闭失败必须绑定真实可制造的原因和对象状态；不能只让桩返回错误而保留与该
  错误码矛盾的注册、句柄或资源状态。
- 服务或进程已经退出后，后续操作前必须先显式重启并等待恢复。对象或连接已失效后，不得继续
  使用旧对象观测结果；应重建资源或改用管理接口、日志和新连接。
- 一条用例只使用一种构建类型、运行模式和唯一终态。Debug/Release 或不同后端的对照必须拆开。
- `steps` 的每项直接绑定 `action` 和 `expected_result`，每个预期只有一个可判定的正确产品结果，不写“A 或 B”。风险用例在暴露缺陷的步骤另填 `failure_observation`，表示命中即 FAIL 的当前错误观测。
- 逐行朗读时，右列必须是左列动作完成后立即可判断的结果。若左列是“记录/读取/检查本次返回值”，
  右列只能写本次记录到的值，不能提前写下一次调用、下一字段或最终状态；发现错位时整张两列表重建。
- 一次只处理一条用例：按执行顺序直接写
  `steps=[{"action":"业务动作","expected_result":"正确产品结果","failure_observation":"当前错误观测，出现即 FAIL"}]`；非风险步骤可省略失败观测，不要把动作和预期拆成两个数组。
- 触发风险的业务动作与其完整调用后状态必须放在同一个 step：`expected_result` 同时写返回值、错误
  原因和本次动作后需要判断的状态；`failure_observation` 用相同字段顺序写当前错误实现。后续“检查
  状态”步骤只能原样复核这组值，不能改成成功路径的计数或布尔值。正确修复若只改变错误传播，
  就只改变返回值；不得臆造失败 callback 或后续 callback 已执行。
- 前置条件只描述第一步前已经成立的状态；测试中的配置切换、重建、恢复和再次发送都写成
  独立步骤并给出对应预期。
- 清理动作不得重复释放已在失败路径中释放的资源；需要时重建或重启拥有该状态的进程。

## 自查

写完后只检查一次：不了解源码的测试人员能否仅凭产品正常入口执行，能否从外部结果判断成功
或失败，步骤之间是否矛盾。若不能，继续向上转换操作层级；若不存在可靠外部入口或观测方式，
诚实保留为 `Developer-confirm`，不要伪造可执行用例。
