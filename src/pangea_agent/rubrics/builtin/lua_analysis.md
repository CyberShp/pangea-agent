# Lua 源码分析方法

目标是还原 module 的真实运行流程，再把可证明的失效条件转成可执行测试。优先使用 inventory 中的 `requires`、`module_exports`、`state_writes`、`protected_calls`、`coroutine_calls` 和函数/分支信息定位入口与高风险路径，并回到冻结源码逐行确认。

## 语言语义基线

- 只有 `false` 和 `nil` 为假；`0` 与空字符串都为真。
- `and` / `or` 会短路并返回操作数本身，不保证返回布尔值。
- 访问缺失字段得到 `nil`；调用 `nil`、对 `nil` 做不支持的运算或使用非法 table key 会抛错。
- `:` 调用会隐式传入 `self`，`.` 调用不会。定义方式与调用方式不一致时，沿参数绑定继续追踪实际结果。
- table、function 和 userdata 按引用共享；赋值可能形成别名。修改嵌套 table 时要追踪所有可见持有者。
- `pairs` 遍历顺序没有保证；长度运算符对带空洞的序列不提供稳定边界。
- metatable 的 `__index`、`__newindex`、算术/比较和调用元方法可能改变普通字段访问与运算行为；`rawget` / `rawset` 会绕过相应元方法。

不得把 C/C++ 的真假值、空指针、整数边界、栈对象生命周期或线程模型直接套到 Lua。

## Module 与依赖

从每个入口追踪：

- module 返回值、公开函数、加载时执行的语句和对外注册动作；
- 字面量 `require` 的仓库内依赖、外部依赖和候选不唯一依赖；
- 动态 `require` 表达式的取值来源及允许的 module 集合；
- `package.path` / `package.cpath`、宿主注入路径、预加载 module 和生成代码对解析结果的影响；
- module 加载顺序、循环依赖、加载失败与重试后的可见状态。

`require` 会缓存成功加载的 module。共享 module table、加载时副作用和缓存状态要按实际 Lua VM/宿主隔离边界判断，不能默认是进程全局或请求私有。依赖为外部库或生成文件时，把它当作有明确接口边界的上下文；只有缺少该接口会阻止当前行为判断时才记录 `UNRESOLVED`。

## 状态、分支与错误

重点追踪：

- module table、对象字段、非局部变量、闭包 upvalue、缓存和注册表的读写顺序；
- `if` / `elseif`、循环、提前 `return`、多返回值截断/补 `nil` 和可变参数传播；
- `error`、`assert`、`pcall` / `xpcall` 的返回形状、错误对象、handler 结果与调用方分支；
- protected call 发生前已经完成的状态或资源副作用，以及失败后是否回滚、重试或保持部分完成状态；
- 边界处传入 C library、userdata、FFI 或宿主框架的值、所有权和错误约定。

protected call 只隔离 Lua 错误传播，不自动恢复之前的副作用。缺少显式校验或回滚不自动构成风险；必须证明特定输入和控制流会产生错误的外部结果。

## Coroutine 与资源生命周期

对 `coroutine.create` / `wrap` / `resume` / `yield` / `status` 形成完整状态图：创建者、首次启动、每个挂起点、恢复参数、多返回值、错误状态、终止和再次恢复。宿主框架的任务/消息协程也按其调度契约判断并发与隔离，不能默认等同于 OS 线程。

文件、socket、timer、锁、订阅、RPC 句柄和 userdata 要追踪创建、发布、使用、关闭、取消、超时、重试和异常退出。GC 只能证明对象可回收；资源何时释放、finalizer 是否执行、常驻内存是否回落仍需源码或运行契约支持。

## Coverage 与测试转换

Coverage 是补测提示，不是语义正确性的证明。当前任务若提供已匹配到 Lua symbol/branch 的 Coverage gap，逐项闭环到复用用例、新用例或不可达结论；没有匹配记录时不得推测某行已覆盖或未覆盖。

每个风险先写清：

1. 可由测试人员制造的输入、状态、时序或依赖故障；
2. 从入口到失效点的真实控制流和状态变化；
3. 系统结果、外部观测点和恢复标准；
4. 会排除该风险的保护分支、宿主契约或调用方约束。

用例优先采用公开入口、消息、RPC、配置、文件或设备状态表达。函数、table、分支和行号只作为源码证据，不把内部实现步骤冒充黑盒操作。
