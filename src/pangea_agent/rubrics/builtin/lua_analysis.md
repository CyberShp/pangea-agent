# Lua 源码分析方法

本规则只处理 Lua 语言本身的语义。框架专属行为由 task 的其他
`checkpoint_rubric_paths` 补充；不要把通用 Lua 结论冒充为框架契约。

重点抽取：

- 顶层执行代码、全局函数、局部函数、表函数与 `:` 方法。
- `require` 依赖、模块返回值、入口函数和直接调用关系。
- `if/elseif/else`、循环、提前返回、错误分支和协程切换。
- 显式资源获取、释放、注册、注销、重试、停止与恢复。
- `error`、`assert`、`pcall`、`xpcall` 及错误传播后的部分副作用。

分析调用时必须区分 `object.method(object, ...)` 与 `object:method(...)`。二者只有在
真实接收对象和参数一致时才能视为等价；不要因为函数名相同就合并调用链。

`pcall` 或 `xpcall` 捕获错误只证明调用方收到了错误结果，不证明被调函数已经回滚。
继续检查失败前已经完成的表写入、资源注册、外部调用、回调执行和状态迁移，以及调用方
后续重试、停止或恢复是否仍成立。

Lua 表中缺失的 key 读取结果是 `nil`；只有对 `nil` 或其他不可索引的接收者继续取字段时才会
直接报错。对 `config=nil`、`config={}` 和 `config={dependency_ready=false}` 必须分别重放，
不能因为最终都涉及 `nil`/假值就合并触发点或副作用。记录状态和审查预期时也严格区分
`nil`、`false`、`0`、空字符串和空表，不用一个近似布尔值代替未赋值状态。

Lua 的 `error` 经 `pcall` 返回的错误对象可能包含源码位置。冻结的上层入口没有对错误文本做
归一化时，黑盒风险和用例只固定成功标志以及可稳定确认的消息片段，不把完整错误字符串相等
作为唯一预期。

`require` 通常按当前 Lua VM 的 `package.loaded` 缓存模块。区分首次加载的顶层副作用与缓存
命中后的行为；只有冻结源码明确清除缓存或使用其他加载入口时，才分析重复执行模块顶层代码。
参数不是静态字符串时保留为动态依赖，不猜测目标文件。

用例声称通过清理 `package.loaded` 获得全新状态时，必须清除并重新 `require` 持有旧类表、模块表、
signal、callback 或闭包引用的完整依赖链，并丢弃测试侧旧引用；只清底层模块但保留仍引用旧对象的
上层模块不算等效重置。无法证明完整重置时，每条用例使用新的 Lua 进程或 VM。

协程风险必须写明谁创建、谁 `resume`、在哪个条件 `yield`、错误如何返回，以及停止或取消时
谁负责释放外部资源。仅看到 `yield` 或 `resume` 失败不足以证明死锁、泄漏或无法恢复。

Lua GC 的触发时间不确定。内存对象最终可回收不等于文件、句柄、设备、订阅或原生资源已经
及时释放；反过来，也不能在没有持续引用或外部资源证据时把暂未 GC 直接写成泄漏。

元表、动态字段、运行时拼接模块名和注入的全局函数若无法在冻结范围中唯一解析，明确记录
未确认边界，不用猜测补齐调用链。Lua 与原生扩展的边界同样只按 task 已冻结的契约和实现判断。

最终输出仍应先转换成测试人员可制造的业务条件、可观察结果和恢复标准；函数、表字段、模块名
与行号只作为证据。
