# Markdown 叙述优先规则

本文件是深度型 Bootstrap 强制规则。未读取并 ACK 前，不得创建分析工件。

## 一、主事实载体是 Markdown 活文档

本 Skill 的分析内容必须首先写入 Markdown，而不是先写 JSON 后等最终汇总。

Markdown 活文档承担：

- 开发实现讲解；
- 流程、分支、状态和资源解释；
- 异常因果链；
- 风险点；
- SFMEA；
- 测试场景、测试流程和测试用例；
- 覆盖审计。

JSON 只允许用于：

- 运行状态；
- 运行计划；
- 输入材料机器索引；
- 独立审查状态。

JSON 不得作为分析内容的唯一版本，也不得作为用户主要交付。

## 二、禁止“表格即分析”

表格用于索引、对比和追溯，不能代替自然语言讲解。

按实际需要在重要表格旁解释：

- 这张表描述的是什么；
- 为什么这些项重要；
- 项目之间有什么因果关系；
- 测试人员应如何理解和使用；
- 哪些项风险最高；
- 哪些内容仍不确定。

禁止只输出大表而没有叙述。

## 三、Flow Card 必须是完整文章

每个核心流程是独立 Markdown 文件，frontmatter 可保留 ID 和状态，正文按执行顺序讲解。五阶段流程的可展示步骤按 business-flow-projection.md 在同一文件的 pangea-flow 内容块保存；投影引用文件，不重复维护另一套步骤。内容块只承担可读取字段，不能替代下面要求的推导正文。

正文必须像熟悉代码的开发带着测试人员过流程：

- 先讲用途和上下文；
- 再讲外部如何进入；
- 按时间顺序讲正常流程；
- 逐个解释分支进入条件；
- 解释状态和资源变化；
- 解释异常怎样传播；
- 最后转换为黑盒测试。

不得以 JSON Object、字段清单或函数列表代替叙述。

## 四、正式输出必须边分析边更新

不能等全部 JSON 写完后，最后才生成 Markdown。

每个流程形成结果就更新 Markdown 活文档并发布投影；正式输出仅在最终交付阶段发布已审版本。

后续发现新证据时：

1. 更新事实；
2. 更新受影响 Flow Card；
3. 更新风险、SFMEA 和测试追溯；
4. 更新阶段投影；交付阶段再发布正式版本。

## 五、终端不得倾倒 JSON

终端只展示：

- 本步骤完成情况；
- 关键分析结论；
- 生成或更新的 Markdown 文件；
- 阻塞和下一步。

不得把 JSON 内容当作报告打印给用户。

## 六、模块分析不设篇幅门槛

模块分析不检查最低字符数、固定章节或叙述长度。简单流程可简短，复杂流程按适用维度深入。是否解释充分、证据成立、遗漏重要分支，由 Agent/Reviewer 判断，不由脚本按关键词或篇幅裁决。
