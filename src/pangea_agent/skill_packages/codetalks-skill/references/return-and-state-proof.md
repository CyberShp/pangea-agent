# 返回值与状态核对

生成用例和审核用例都使用本方法。核对记录写入已有分析正文或复核记录，不新增交付文件或机械语义门禁。编号步骤仍使用现有用例模板。

## Producer：先求值，后写预期

1. 固定一个可构造初态，区分环境初始化与业务准备。为相关状态命名，记录已知值；未知值保留为未知，不按零值计算。
2. 按实际执行次序，从准备到观测再到清理，为每次调用求值。读取冻结实现，写出本次实际经过的判断及真假、执行的赋值/子调用、最终 return；证据标明路径与具体语句。分支没进入、return 后面的语句不执行。子调用先算完，再回到调用者继续；不按函数名或错误码猜副作用。
3. 状态从上一调用的结果传递。记录本次修改的值和需要保留的值，未执行赋值的字段沿用调用前的值。对验证“保留”的目标，在合法接口允许时先构造有区分力的值，避免原值恰好为零掩盖错误清零。
4. 在分析正文以 Case ID 留下执行表：步骤号、调用/输入、调用前状态、实际命中的判断与执行语句、返回值、调用后状态、源码依据。先完成这张表，再据此写用例。不要从已经写好的预期倒填证明。
5. 用例中的每个状态断言标明观测时点，例如“步骤 3 返回后”。分开记录主要触发后、所有验证操作结束后、清理操作结束后三个时点；相同时可以明确引用前一时点。后续重试、重新连接或查询也要按源码判断是否改变状态，不能继续沿用触发后的状态。
6. 所有实际要执行的业务调用放入一套编号步骤，含准备、后续验证及清理。预期、观测和清理栏目引用步骤号，不偷偷增加调用，不提供多个可选执行顺序。无需清理时说明最终保留的状态及为何可结束实例生命周期；“释放资源”不能扩大为“全部状态归零”。

预期的依据需要区分：设计/接口契约规定的应有行为、冻结实现推演出的实际行为、真正执行后的观测。若契约与实现冲突，保留差异作为风险或待确认，不能为了让当前代码通过而改写契约；只有源码时明确标注为实现行为回归。未真正执行不得称为实测。

## Reviewer：独立求值，再对照

先从用例取出初态和操作顺序，暂不采纳其预期与 Producer 的执行表。独立读取冻结源码，按上面的方法计算返回值和状态，写入复核记录后，再逐项对照用例及 Producer 证明。

发现差异时记录：Case/步骤号、原断言、独立计算结果、实际控制流（包括提前返回）、支撑语句、受影响的后续步骤及三个观测时点。给出替代操作前也独立计算一遍；不能仅凭一处赋值存在，就认定本次执行经过它。

Producer 收到修改建议后重新读取相关语句并求值，记录接受或驳回的依据。不要因为意见来自 Reviewer 就覆盖原预期。原 Reviewer 复查完整受影响用例，尤其是修改点之后的状态传播，以及正式文档的预期、观测、清理是否仍引用旧时点。

返回值或最终状态存在已证实矛盾时，必须交回原 Producer 定向修订；尚不能求证时保留 UNRESOLVED 和具体缺失证据。源码引用齐全、表格完整或其他用例正确不能抵消该矛盾。语义裁决属于 Reviewer，宿主只负责路由和真实状态记录。

## 常见错误

- 看到后面有赋值就采用新值：先检查本次调用是否已经 return，以及赋值所在条件是否成立。
- 主操作没有副作用就写“本例未改状态”：准备、验证和清理也是本例的一部分，分别计算对应时点。
- 清理后又做业务验证，仍宣称结束时已清理：按最后一条实际操作求末态，需要恢复时把恢复动作加入步骤。
- 用被测程序输出直接生成期待值：执行可以反证实现推演，不能代替独立契约或预先确定的断言。
