# 阶段 03：路径分析与独立补测

## 可直接执行的库接口用例

当被测对象是依赖齐备、可独立执行的公开 C 库接口时，读取 references/executable-case-review.md，在每条用例的操作步骤中直接提供完整 C 程序。初始化、准备、触发、观测、清理和对应数值断言都写在这一个代码块中；正文说明目标、证据和适用边界，预期结果引用代码里的比较，不再重复一套值或末态总述。这样 Reviewer 执行原用例本身，无需重新解释文字中的操作。代码只调用真实实现，不重写业务逻辑。其他对象仍使用受支持的业务入口，无法执行时如实记录限制。

## 返回值与末态：本阶段直接执行

先把每条用例的初态和全部操作列出来，再计算预期。Reviewer 先独立计算，不复制 Producer 的预期或执行表。按每次实际调用，从函数入口逐句到本次 return：引用实际判断的原文，代入本步输入及上一步状态，求出真假；只执行进入分支内的语句。写出本次真正执行的赋值和子调用，以及已经 return 因而没有执行的后续赋值。没有执行的赋值不能改变状态。

通用例子（只说明推演方法，不能复制成项目用例）：
```c
int update(int valid, int *value) {
    if (!valid) return -9;
    *value = 7;
    return 0;
}
```
若调用前 value=2、valid=0，则 !valid 为真，立刻返回 -9，value 仍为2；后面的 value=7 没有执行。错误返回码不能与“设置成功后的状态”混用。若真实代码先赋值再返回错误，则保留已经发生的赋值，不能反向套用“错误一定无副作用”。

用例只保留一条执行序列：步骤 0 初始化 → 编号准备调用 → 主要触发 → 观测 → 清理。步骤 0 写明实际初始化方法和影响断言的初始值；前置条件只列环境、权限、接口和可用夹具，不再存放业务状态。每次调用记录本步返回、变化和保留状态，后一步接着前一步的实际结果执行。循环必须展开核对每轮的准备和触发，不能沿用首轮初态。预期和清理说明引用步骤时点，不另加调用或可选顺序。

清理例子：若 reset 只执行 active=0，调用前 active=1、total=4，则调用后 active=0、total=4；不能写全部归零。若随后为了验证可重用而执行 start，使 active=1，则验证结束时 active=1；如要结束时 active=0，必须在步骤中再执行真实 reset。分别给出主触发后、全部验证后、清理后三个时点的结论；同一状态可以明确引用前一时点。

逐条将文档的返回值和状态断言与这份计算比较，包括“全部”“恢复初始”“没有变化”等总述。发现矛盾时，由原 Producer 修正所有受影响的后续步骤、预期及清理，再由原 Reviewer 从初态重算；审核建议本身也要用同样方法核实。不能用“符合源码”一句话、行号引用或表格齐全代替求值。证据不足保留具体未决项，不给数值正确性 PASS。

设计契约与实现不一致时保留差异，不能为了通过执行而改写契约。只有源码时标注实现行为回归；未执行的推演不能称为实测。更完整说明见 references/return-and-state-proof.md，但以上方法直接在本阶段执行，不依赖另一次文件读取。

使用模板的步骤 0 作为唯一初态。先按支持的初始化方式创建实例，再执行后续准备；不能用“新建实例”暗指所有字段已经置零。
每次调用分别写预期返回值，查询接口返回的数据不混入动作接口的成功码。断言完整描述实际清除和实际保留的状态；只有逐项核对全部相关状态后才能使用整体结论，不能用局部正确的字段列表支持“全部重置”等更强结论。
按以下顺序处理每个候选用例，而不是先批量写步骤再补预期：
1. 从缺口台账选定主要验证目标及一条目标路径，写出要区分的正确/错误行为。
2. 在覆盖缺口分析正文中按 Case ID 列出简短的执行核对表：步骤/调用与输入、调用前关键状态、按源码得到的返回值、调用后变化与保留状态、命中判断的源码位置。准备调用、主要触发和清理均按原文顺序核对，不跳步；不使用“全部成功”代替各调用的实际结果。准备调用提前失败时，从失败后的实际状态继续推演；不能把希望设置的值当成已经设置成功。
3. 将这条推演写成可独立执行的用例。不同参数导致不同路径或预期时拆为独立用例；同一路径及同一预期的等价数据可共用一例。只有额外交互行为需要验证时才增加组合用例，并写明独立用例尚未验证的交互断言。
4. 写出需要改变、需要保持不变的可观测状态，以及恢复动作。无需清理时说明理由，例如使用独立的局部实例且未持有外部资源；已有释放调用不代表所有字段归零。
5. 回填台账中的用例 ID 和具体断言。区分“作为准备调用经过”“由主要触发及断言验证”“待验证”。只有准备步骤经过目标函数，不足以声称其行为已验证；先查现有断言是否充分，再决定补例或补充已有用例。
收到 Reviewer 修订意见后，先按上述执行表验证建议本身，再改用例；建议同样可能违反保护条件。若建议不成立，保留问题 ID 并提供首次不成立的调用、实际返回值及可行修订，交回同一 Reviewer。交付用例只保留一套确定的可执行步骤；被否定的尝试和推理纠错放入复核记录，不能混在操作步骤里让测试人员挑选。改过中途或末尾操作后，重新核对最终状态和清理说明。
无法通过支持接口构造的状态，明确所需测试夹具、允许的注入边界及依据；夹具条件尚未成立则记为待确认，不假装现成可执行。保持正式用例、待确认设计和范围外记录的真实区别。
每条正式用例从模板展开完整的前置条件、操作步骤、预期结果、观测方式、清理和复原。不要等交付阶段再用通用句子补齐：观测必须能判本例 Oracle，恢复必须回到可重复执行状态。对库接口示例，初始化写明确（例如新建全零实例），有待处理状态必须写出构造它的支持操作。不要直接将源码字段值当作已经完成的环境准备。
只为已确认目标路径生成补测；范围外或待确认缺口保留在台账及未决项，不生成占位 Case ID 放入 test_cases。相同初始状态、主要触发和预期的重复用例应合并保留一个稳定 ID；不同预期路径必须拆例。最终发布前核对 FLOW/BRANCH 关联和正文一致，不能靠添加范围外占位用例消除关联空值。
读取 references/path-and-case-design.md 的用例边界，以及 references/business-flow-projection.md。
对目录中每条范围内路径连续完成：读实现与接线 → 从支持入口构造触发 → 分析保护、状态/资源耦合与异常恢复 → 反证和可达性核对 → 独立可判定的补测设计。
活文档/覆盖缺口分析.md 维护缺口与 FLOW 的关联摘要；每条流程的主干和分支在 活文档/流程讲解/流程-<FLOW-ID>-<名称>.md 内按 business-flow-projection.md 的 pangea-flow 内容块保存，详细推导在该文件展开。投影引用 document_path，由 publish-stage 读取步骤，不再另抄一份主干/分支。缺内容保留待补齐，不只发布流程名称。
活文档/黑盒测试用例.md 按模板逐例保存。一个独立验证目标一个用例；不同关键参数或不同预期路径分别成例。准备、观测和清理可共用，不把独立目标拼成连续操作。
同一用例可以自然关联多个 gap_id 或 FLOW，但说明本次执行如何进入各条相关路径；不能把“关联了用例”当作覆盖缺口已经补齐。真实跨模块耦合可单独成为验证目标，不按模块名称禁止组合。
不能触达记录依据；无法确认的路径保留未决。即使同一共享函数已有关联用例，其他相关分支仍须有分析和处置。
风险仅在发现真实失效机理时生成；不要求风险文档或 SFMEA 占位。每条路径形成成果即更新台账、投影和 progress，避免全量重写。
