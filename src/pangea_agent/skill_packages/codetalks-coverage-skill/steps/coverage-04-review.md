# 阶段 04：复核与定向修订

判定路径不可达前，分别检查实例初始化、成功赋值、失败后的保留状态、清理及重用、外部输入。某个设置接口拒绝一个值，不证明下游永远见不到它；需有证据证明所有受支持入口和初态都排除该状态。尝试从最小合法初态给出反例，不要默认必须先成功调用某个准备接口。证据不足保留未决，不能删除对应补测来消除矛盾。

## 返回值与末态：本阶段直接执行

先把每条用例的初态和全部操作列出来，再计算预期。Reviewer 先独立计算，不复制 Producer 的预期或执行表。按每次实际调用，从函数入口逐句到本次 return：引用实际判断的原文，代入本步输入及上一步状态，求出真假；只执行进入分支内的语句。写出本次真正执行的赋值和子调用，以及已经 return 因而没有执行的后续赋值。没有执行的赋值不能改变状态。

通用例子（只说明推演方法，不能复制成项目用例）：
```c
int update(int valid, int *value) {
    if (!valid) return -9;
    *value = 7;
    return 0;
}
```
若调用前 value=2、valid=0，则 !valid 为真，立刻返回 -9，value 仍为2；后面的 value=7 没有执行。错误返回码不能与“设置成功后的状态”混用。若真实代码先赋值再返回错误，则保留已经发生的赋值，不能反向套用“错误一定无副作用”。

用例只保留一条执行序列：步骤 0 初始化 → 编号准备调用 → 主要触发 → 观测 → 清理。步骤 0 写明实际初始化方法和影响断言的初始值；前置条件只列环境、权限、接口和可用夹具，不再存放业务状态。每次调用记录本步返回、变化和保留状态，后一步接着前一步的实际结果执行。循环必须展开核对每轮的准备和触发，不能沿用首轮初态。预期和清理说明引用步骤时点，不另加调用或可选顺序。

清理例子：若 reset 只执行 active=0，调用前 active=1、total=4，则调用后 active=0、total=4；不能写全部归零。若随后为了验证可重用而执行 start，使 active=1，则验证结束时 active=1；如要结束时 active=0，必须在步骤中再执行真实 reset。分别给出主触发后、全部验证后、清理后三个时点的结论；同一状态可以明确引用前一时点。

逐条将文档的返回值和状态断言与这份计算比较，包括“全部”“恢复初始”“没有变化”等总述。发现矛盾时，由原 Producer 修正所有受影响的后续步骤、预期及清理，再由原 Reviewer 从初态重算；审核建议本身也要用同样方法核实。不能用“符合源码”一句话、行号引用或表格齐全代替求值。证据不足保留具体未决项，不给数值正确性 PASS。

设计契约与实现不一致时保留差异，不能为了通过执行而改写契约。只有源码时标注实现行为回归；未执行的推演不能称为实测。更完整说明见 references/return-and-state-proof.md，但以上方法直接在本阶段执行，不依赖另一次文件读取。

对每条用例，在现有复核记录中按步骤列出简短执行核对表：调用与输入、调用前关键状态、源码实际返回值、调用后变化及保留状态、源码位置。将这个独立结果与用例逐项比对，具体指出第一次不成立的步骤；不能用一行“正确/已修复”替代执行核对。已读过的实现可以引用同一源码位置，无需反复读取整份仓库。
Reviewer 提出的替代步骤也先作同样核对；不能只修最后的断言，留下无法成功的准备调用。不可达结论须检查合法初始化和其他支持的进入路径，某一种准备方式失败不等于目标不可达。复查修订稿时重新按完整顺序核对受影响用例，不只看被点名的一行。
按测试人员照原文执行的顺序核对，不按你猜测作者想表达的操作补齐条件或省略动作。从步骤 0 的实际初态逐步累积状态；若原文其他位置另列初态，先核对是否矛盾并交原 Producer 澄清，不能自行忽略。检查每次调用的预期，包括查询返回的数据，而不是只看最终状态。
对预期中的整体结论核对其完整范围：源码只修改部分字段时，验证明确保留的字段，并检查正文是否误称全部状态重置。不能因为旁边列出的几个字段正确，就忽略更强的错误总述；修订同一用例中的目标、步骤、预期和观测文字，保持含义一致。
先独立读取冻结源码，列出目标内入口的正常出口、提前返回条件和关键副作用，再与 Producer 的路径台账、用例逐项比较。不要从 Producer 的 PASS 或关联表反推源码行为。
在现有复核记录中逐 Case 留下一行核对结果：目标路径、准备步骤是否真正到达、主要触发是否执行、返回值/变化与不变状态是否正确、观测与恢复是否成立、源码依据、发现的问题 ID。逐条写具体判断，不复制“符合源码”。再反向从台账检查漏测，特别检查只在准备步骤出现的未覆盖函数。
至少尝试这些反证：准备接口是否先拒绝输入；先前调用是否已经改变后续分支；失败返回是否仍产生副作用；清理是否只清除部分状态；组合用例是否只是重复两个独立目标。反证按源码适用性选择，不要求捏造问题。
Reviewer 将问题及最小修改要求交回原 Producer；Producer 仅修订受影响的原用例、分析与关联，保留稳定 ID；Reviewer 再对修改内容及受影响关联复查。复核记录同时保存发现、修改和复查依据。无法证实的结论保留 UNRESOLVED，不用“字段齐全”抵消语义问题。
正式用例必须只有一套当前有效步骤；若混入失败尝试、“重新理解”或多个互相冲突的修正版本，交回 Producer 整理并重新核对。原始错误和驳回理由留在复核记录供追溯，不留给执行者猜选。
缺口路径为空时检查 Producer 是否确实在冻结源码中查找过原始标识；已读取的候选实现必须保留其证据，不能用“未定位”覆盖已知事实。逐条对照正文、范围台账及投影，移除误列入正式 test_cases 的范围外/待确认占位条目，未决本身继续保留；无法构造初态、无法独立观测或恢复的用例不得描述为已可执行。

速度型自审也必须逐例重新读取相关冻结源码，不能用“字段齐全”“每分支独立可判定”替代审查。按 references/path-and-case-design.md 的执行轨迹，在现有复核记录中逐 Case 写出：主要触发、准备状态是否可达、每一步返回值/状态的源码依据、声称关联的分支是否真的进入、与其他 Case 的独立目标边界。发现不同输入/结果藏在同一 Case 时拆为独立 Case ID，并同步分支关联；共享准备保留为准备步骤。
从目标行为独立重查每条范围处置。仅因“有 FLOW”“在同一文件”“被列为零覆盖”不能保留 in_scope；列出具体调用、状态或资源影响链及其证据，没有影响链则依据证据排除或记 unresolved。
复核完成后列出本轮实际纠正的错误和仍未解决的问题；没有发现问题也展示逐例核对依据。PASS 仅表示本次设计复核结论，不能把设计路径说成实测分支覆盖、执行成功或覆盖率提升。不能证明充分性时记录明确遗漏/不确定项，不写“所有路径均已覆盖”。

深度型由宿主启动与 Producer 分离的真实 Reviewer，读取 `references/worker-judge-protocol.md` 的 Judge 要求。
先读取 references/path-and-case-design.md，核对目标入口/路径目录与范围处置：范围外有据、共享实现不越界、相关耦合与异常恢复不遗漏。
复核流程主干是否实际提供，缺口与用例是否能追到具体路径；每条用例能否独立判定，关键输入/结果不同的场景是否误合并；多缺口关联是否由同一次自然执行实现。
复核覆盖来源/缺口定位、入口/分支、源码证据、实际参数类型、保护条件、支持范围、异常传播、遗漏以及测试的外部可执行性、独立观测、Oracle 和恢复。主动尝试反例，不能只重复 Producer 结论。

集中写 `活文档/复核记录.md`：review_issue_id、受影响 Flow/Risk/Case ID、证据、保留/驳回/合并/未决及理由、原文件路径、Producer 定向修订和 Reviewer 复查结果。
直接修订受影响的原缺口分析、风险或用例，同步台账与投影；不重开阶段 03、不清空完成状态、不重新写全部报告。阶段 04 内可以多次 progress/publish-stage，新增发现保持稳定 ID。
在现有 `内部索引/独立审查状态.json` 记录 independent、checked_artifacts、真实会话 ID/调用证据、semantic_verdict（PASS/UNRESOLVED）和 summary。不得伪造身份或把自审说成独立审查。
深度型无法独立复核时保存当前进度并报告受阻；不要切换 speed 绕过。复核结束但争议未解可记录 UNRESOLVED，正式报告必须呈现；待分析内容仍是未完成。

深度型读取 `references/executable-case-review.md`，按宿主当前 review_request_id 先写逐例执行计划及程序，等待宿主真实记录后再下复核结论。执行失败或未验证只记录证据，不停止其他用例；Reviewer 不代 Producer 改用例。正式交付保留逐例可采纳/需修订/未验证、分子分母、理由及执行记录引用，不把退出码 0 当作质量验收。
