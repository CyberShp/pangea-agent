# 业务路径与独立用例

在盘点流程时读取前两节，在生成用例时读取后两节。模块分析和覆盖率分析使用相同的业务粒度，深入范围可以不同。

## 流程、路径、分析组

独立外部入口或业务目标通常形成 FLOW；同一目标下条件和结果不同的行为作为 BRANCH。独立配置、建立、运行中操作、终止/恢复等是否分为不同流程，以真实入口、生命周期和契约为依据，不固定流程数量。
分析组用于共享源码阅读；不能因同目录、同协议、共享函数或共用准备环境，把多个业务目标压成一个流程名称。
先做目标范围内的轻量入口/路径目录，包含相关正常、拒绝、异常、恢复及交互路径，再深入分析。目录写入现有台账，不新增报告或阶段。没有证据的路径标待确认，不先编造完整架构。
从入口向实现与从缺口/候选向入口双向核对。重要相关行为有独立条目或有依据地链接等价路径；不得因为只优先读了少数入口而宣称全部分析完毕。

## 跨模块与耦合

范围是目标行为，不等于文件或函数集合。纳入共享实现时说明：目标入口 → 调用/共享状态/资源 → 对目标正确性、安全、状态或恢复的影响。
同文件或间接调用关系本身不足以把其他功能全部纳入。前置认证、共享清理、协议间状态交互等须按真实接线判断；没有证据时待确认，不按名字猜测相关性。
补读依赖用于理解上述影响链，不扩大用户要求的补测目标。
使用目标外的支持接口完成准备，不等于为该接口扩展独立补测目标；该接口在覆盖率报告中已覆盖也不妨碍作为准备。按本例主要触发和实际断言判断范围，不能仅因准备函数不在零覆盖清单中而驳回用例。

## 一条用例的边界

先在现有分析正文中为每个候选用例核对一条执行轨迹：可构造初始状态 → 准备操作及其真实返回值 → 唯一主要触发 → 实际命中的判断/提前返回 → 剩余状态 → 可观测 Oracle。逐步读冻结实现，准备步骤同样受保护条件约束；不能只核对最后一步。若前一步失败或改变状态，必须据此重新推导后续操作，不沿用期望中的状态。
例如同一入口的“已占用”“输入无效”“未授权”是不同条件和结果，应分别有 Case ID；在一个用例下写三个分支小节或“各分支独立初始化”仍未完成拆分。相同路径和预期下的等价参数可以作为同例数据，不需机械穷举。
反例：先进入禁止配置的运行状态，再把配置步骤预期写为成功；只验证准备接口拒绝，却宣称覆盖了目标入口的拒绝分支。必须确认主要触发确实执行并命中本例声称验证的路径。
如果只能调用公开库接口，明确其为支持的测试入口及返回值契约；若只看得到内部实现，没有外部操作或观测接口证据，记录 UNRESOLVED，不编造管理命令、状态查询或可执行性。

一条用例具有明确的初始状态、主要触发和验证目标，能独立执行、独立判定。名称和预期明确要区分的外部行为。
关键输入取值导致不同路径或预期时，分别给出独立 Case ID、操作和预期；可以共用准备方法，不能让执行者从“依次尝试多种参数”自行拆例。
不同业务验证目标、成功与拒绝/异常处理、相互独立的故障场景分别设计。一个独立目标的失败不应遮蔽下一个独立目标的判定。
合法的端到端场景可以跨多个 FLOW/函数：前置步骤、自然执行链、同一目标的多种观测和恢复可以在同一例中。真实耦合故障以具体交互作为单一验证目标，不为耦合本身禁止联合测试。
操作写出可执行动作，主要触发应清晰可定位；不能在一个编号里藏入多项独立测试。预期给出具体响应、状态或事件及判断依据，观测和失败解释围绕本例目标，避免每例复制同一段泛化描述。
不是一步一用例，也不是一函数一用例；不穷举循环/并发的所有内部排列，不用关联数量判断粒度。

## 缺口追溯与验收

在现有台账和分析正文中留下双向核对：从每条目标路径找到用例的主要触发与断言，再从每条用例返回它实际到达的路径。函数仅作为准备调用经过时注明这一事实；没有验证其关键结果不能宣称该行为已验证。补充正常路径、拒绝路径还是保持待确认，由源码和现有断言决定，不机械要求一函数一例。
预期区分调用后改变的状态、应保持不变的状态及资源归属。恢复说明应与本例留下的状态对应：局部实例没有外部资源时可说明退出作用域即可；清理接口只重置部分状态时，不把其余字段写成归零。相同文字只有在实际机制相同时才可复用。

每条用例说明外部操作怎样进入所关联的路径；关联多个缺口时，说明同一次执行怎样自然经过它们。禁止为了增加关联函数数量，在步骤中串接几个独立测试。
用例已设计不代表已执行或覆盖提升；仅有函数覆盖率不能证明内部条件方向，需读源码推导分支。
投影的 test_cases 保留原字段并增加 verification_goal、linked_flow_ids、linked_branch_ids、linked_gap_ids（无相应关系用空数组），与正文使用相同 Case ID。
Reviewer 从路径目录核对遗漏、从用例核对实际触发，检查独立目标是否被揉在一起，不能只数用例或关联函数。
提出“缺少某函数用例”前，检查已有用例是否已通过真实主要触发验证其返回及副作用；调用包装入口可以同时验证它的委托实现，不机械新增同轨迹的另一例。报告仅有函数计数时，不臆测已覆盖次数属于哪个场景。
