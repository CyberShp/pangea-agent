# 分支业务覆盖与稳定流程验收

本轮新增规则只冻结到新 Run：分支 method_version=behavior-branch-v1；四场景 flow_layout_version=stable-v1。旧 Run 使用原 analysis-scene、rubric 快照，不追补新要求。业务覆盖记录是普通 note，不新增结果 schema 或 Python 语义门禁。

## 宿主自动验证

`python verification/branch_behavior_contract.py` 验证新分支无需可选 methodology 即加载专属审核规则；冻结旧 Run 不被升级；覆盖 note 中 missing/unresolved、引用不一致与异常原文仍能保存并继续；新旧流程结构均可消费。此验证不证明模型已能发现所有业务遗漏。

## 真实模型的语义验收样例

下列是验收夹具应明确提供的假设业务事实，不是任何实际产品的默认能力。须提供对应冻结源码及需求/设计，使用真实 worker 执行，再按结果人工或既有 Reviewer 评估；不得用规则文本命中、格式通过或手工预造答案冒充模型验收。

| 夹具事实 | 应发现的业务覆盖 | 不接受的替代 |
| --- | --- | --- |
| 三种受支持策略共用一函数，输出字段随策略改变 | 每种策略有明确输入和预期，实际差异保留 | 仅一条“合法参数成功” |
| 数量允许 1～64，且先检查输入格式 | 0、1、64、65 等边界；边界输入先通过格式检查 | 格式非法样本声称覆盖数量检查 |
| 仅 A 开启、B 可用、状态 C 就绪时允许操作 | 决策规则覆盖关键三因素组合及各类拒绝 | 单项覆盖或 pairwise 宣称充分 |
| 新建后可启动、停止后可重启、删除后拒绝启动 | 前驱状态、操作序列、最终结果有去向 | 三种历史合并成无前置的启动用例 |
| 修改配置只影响后续创建的对象 | 存量对象与后续对象分别验证并恢复配置 | 只查询最终配置值 |
| 管理单元接收参数，后端单元负责应用 | 明确关系 owner，追到消费者与外部结果 | 两单元均假设对方已覆盖 |
| 不支持模式按契约拒绝且现有服务不受影响 | 正常负向行为用例，不生成产品风险 | 把拒绝本身认定为缺陷 |
| 某依赖契约缺失、设施未交付 | 具体 unresolved/readiness 缺口，其他有效结果保留 | 虚构能力、命令或完成状态 |

用例和覆盖 note 双向对账，检查 designed 的真实 case_refs、变体输入与预期；不以用例数量、所有状态均变为 designed 或无风险作为验收标准。简单查询夹具不应被迫输出全部五种方法与无关序列。

## 业务场景与用例粒度验收

依据 [业务用例生成优化方案基线 V1](https://chatgpt.com/space/page_5fc0009351ec8191a9d34492da66eef4)。本次只修改新 Run 的冻结规则与各客户端的规则引用，不实施 Work Agent 拆分，也不新增用例或 note 格式合同。先用同一组冻结源码、资料、目标及明确模型设置验收新版规则；每项记录场景、必要条件、判据、拆合理由和执行缺口，保留原输出供对照。

| 固定样本要求 | 生成验收 | 复核验收 |
| --- | --- | --- |
| 一次关闭处理跨多个函数并经过多个关联判断；资料说明实际关闭与查询入口 | 围绕明确关闭情形写实际动作和结果，内部判断/调用/清理不逐项变成步骤；前置只保留必要条件 | 能识别“置 X、调用 B、观察内部返回 E”及其中文化改写，不凭函数数要求拆例 |
| 同一契约的两个等价实现，一个内联处理，另一个拆 helper 并增加等价守卫 | 业务情形、验证目标和必要判据不随语法结构机械膨胀；真实新增语义须给反证 | 不因多了 if/helper/流程节点要求多例，也不能为保持数量掩盖真实行为差异 |
| 普通关闭与本端主动关闭尚未结束时处理对端 FIN；二者均最终断开，提供 X 的来源、清除点和可用时序设施 | 保留关闭交错的独立验证目标及目标窗口依据，不只交一条泛化“断链成功”；不机械扩成 FIN/RST 乘标记的四格清单 | 要求拆分须指出丢失的业务验证目标；要求合并须证明必要条件、时序、判据和恢复均被保留 |
| 与上一项同样的业务契约和源码，但资料明确没有交付时序控制或注入设施 | 保留有价值设计与具体缺口，readiness 如实为 needs_instrumentation 或 unknown；不虚构命令、桩和已命中记录 | 区分尚未实测与缺设施，不能因缺设施删除场景，也不能把“同时关闭”认作已具备控制手段 |
| 一处注释与实现或需求契约冲突，并包含含义待确认的附带条件 | 区分意图、当前实现、正确预期及未知；既不照抄注释，也不把路径上的每个条件塞入前置 | 对已确定的错误形成精确 finding；无法确认的事实保留 unresolved，不猜外部预期 |
| 提供必要 FIN/RST 报文、抓包入口及现有注入工具；另给仅将内部函数/变量中文化的错误候选 | 保留实际刺激/观测细节；灰盒注入定位与业务主要预期分开；无崩溃不声称无内存破坏 | 不按技术名词判白盒，拒绝中文化内部动作冒充业务步骤；内存安全观察须有依据与设施 |

至少重复执行同一批关键样本，比较业务情形、必要条件和判据的稳定性，记录模型与规则快照；不要求标题和措辞完全一致，不以用例数量或黑盒比例证明粒度正确。覆盖率目标另核对一个业务用例关联多个真实缺口时的实际触发依据；interface-contract 目标允许公开接口的参数、调用顺序、返回与资源契约，不能被强制改成产品 CLI 测试。

以上表格是语义验收要求，不是模型已通过的记录。`verification/branch_behavior_contract.py` 的字节冻结/派发检查、合法 note 的非阻断写入，以及现有用例/流程契约验证均不评价业务语义。没有真实 provider 会话和产物时，语义验收状态保持待验证。

## 稳定性验收边界

- 相同冻结输入和明确身份，仅节点/边/路径数组重排：语义比较不产生虚假增删，展示按显式主路径与稳定身份排序。
- 同起点终点有两条不同条件边：paths.edge_ids 精确区分，不能把两条边一起当作所选执行路径。
- 多条主干或没有适用主干：按 main_path_ids 显示，不猜 paths[0]；缺稳定元数据的旧图照常读取并说明局限。
- 相同输入但本轮发现旧图漏掉真实分支：允许有依据的纠错并解释差异，不能锁定旧错图。
- 明确版本的 flow_baseline/flow_comparison 只供 comparison，普通新建 Analysis 不接收。显式增量 Analysis 仍能读取合同指定的 incremental_parent_records 并重新核验；新稳定规则下独立盲审同时隔离首轮结果、流程基线和增量父记录，旧 Run 保留冻结合同。不得扫描历史 Run 猜测基线，不把未审候选自动批准。

稳定性不是同源码必然生成同答案的保证；输入指纹、证据身份和确定性渲染使差异可解释，业务等价与改动依据仍由 Agent/Reviewer 决定。
