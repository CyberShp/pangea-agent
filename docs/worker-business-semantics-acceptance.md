# Worker 业务语义修改验收

本轮在同一 Analysis worker 内整理业务语义并首次保存用例，不恢复运行时 Reviewer 或 targeted_closure。
验收使用从零编写的合成打印队列，不包含实际用户用例、业务名称、源码或运行记录。

## 输入和答案分离

夹具目录：`verification/fixtures/worker-business-semantics/`。

- C 生成输入仅为 `CONTRACT.md` 和 `queue.c`；Lua 仅为 `CONTRACT.md` 和 `queue.lua`。
- `oracle.json` 是生成完成后的验收依据，不进入生成任务、源码冻结范围或模型上下文。
- 给生成者当前实验分配的冻结规则及上述输入，不提供另一组产物、标准答案、正反例标签或修改目的。
- 创建隔离的实验目录和 source scope，只复制这两份生成输入。不能把整个夹具目录直接作为待分析源码，否则会把验收答案同时交给模型。

## 比较方法

1. 固定源码、独立业务契约、模型、执行器版本、分析目标、并发、工具权限和预算。基线为修改前固定提交，候选为本次修改；记录双方实际冻结规则的哈希。
2. C 与 Lua 分开运行，每种语言每组至少重复三次。每次使用新会话，不继承另一轮答案；交错安排新旧组，降低服务负载变化的干扰。
3. 保存首次提交的原始用例及关联依据，后续修正单独记录，不用修正稿替代首写。首次提交出现无法解析载荷也作为该轮结果，不静默剔除。
4. 评价者先看不带版本标识的首次结果与独立验收依据，逐项记录：行为已设计、具体缺口保留、遗漏、错误断言、无依据设施、准备度矛盾和不可执行表达。允许不同拆合和措辞，不按固定用例数评分。
5. 查看已知重要行为是否保留，以及入口、对象、触发时序、公开观察和清理是否足以执行。不能因移除难测项或全部标 unknown 就认定改善。
6. 从宿主真实时间和调用事件统计首条用例时间、总耗时、读取/写入调用量、模型调用量与可用 token 使用量。缺失数据写缺失，不能用字数估算模型 token 或把手工计时冒充宿主耗时。
7. 先判事实与行为是否退步，再比较可执行性和成本。出现新编造、重要行为遗漏或错误降级即记录退步；质量有收益但耗时增加时单独呈现取舍，不给出全面提升结论。

真实 ACP / provider 的初始、同 action 续接、压缩恢复和格式修复路径应分别保留首写证据。仅在通用模型会话中提供文本属于有限的语义试验，不能声称已经验证产品执行器链路、压缩或实际用户任务。
