# 产品级黑盒用例转换

源码函数、内部状态和协议交互用于理解行为，不直接充当测试步骤。每核实完一条完整行为链，
立即按下面顺序生成流程路径和对应测试用例，再继续分析下一条行为：

```text
源码或协议触发条件
→ 测试环境中对应的产品状态
→ 测试人员使用的正常配置、连接、断开、重连、读写或重启操作
→ 测试人员可看到的连接、设备、IO 或日志结果
```

## 写法

- 步骤只写测试人员通过产品正常入口能完成的操作。
- 只保留触发风险所必需的最少操作；不要同时写“保持连接”和“断开重连”，也不要为解释内部触发机制擅自补步骤。
- 源码中的“触发重认证、发送响应、完成协商”要转换成主机通过正常入口连接或重新连接；不要写“触发、等待、配合某认证流程”等仍要求测试人员理解协议过程的动作。
- 预期只写测试人员能观察到的系统结果。
- “回调完成、队列清空、对象释放、内部资源回收”等源码结论也不能写成主要预期；应转换成 IO 不持续挂起、连接能够恢复、设备继续可用等外部结果。
- 函数名、字段、源码行号、内部状态和认证报文只留在风险证据或原因说明中。
- 协议实现细节不能仅通过换成主动语态就变成黑盒步骤。
- 确实需要打桩或内部故障注入时，只在前置条件中说明“开发预先提供已配置的自动故障环境”，并写清自动触发和自动恢复时机。不能把“开发协助”当成执行步骤。
- 故障前的环境准备或用例结束后的人工复位需要操作内部文件/状态时，用例标为
  `developer_assisted`：内部操作只能出现在 `preconditions` 或 `cleanup`，正式 `steps`
  仍只使用产品入口并从外部判断结果。这种复位是测试环境清理，不得写成产品恢复/
  自愈。只有必须在正式步骤中操作内部状态，或主要 Oracle 就是内部状态时，才归
  `whitebox_support`。
- 读取内部文件、对象或私有状态来判断并发窗口或崩溃时机，也属于内部测试设施：把它放在
  前置准备并标为 `developer_assisted`。只有使用公开测试开关加外部定时、不读取内部工件，
  且结果全部来自产品输出时，才可标为 `business_blackbox`。
- 删除、注销或关闭类系统调用失败时，前置条件必须选定一个真实可制造的失败原因和该原因对应的对象状态；不能只写“底层操作返回失败”，也不能只让桩返回错误而保留原状态。无法稳定制造时标为 `Developer-confirm`，不伪造可执行用例。
- 前置条件已真实制造“对象未注册”或“句柄失效”后，不能预期依靠原注册继续收到事件或完成新 IO；必须先显式重新注册或重建资源。
- 风险只能靠畸形报文、字段篡改或传输故障触发时，把自动故障环境写在前置条件；测试步骤仍是测试人员正常连接、读写、断开或重连。测试人员不得手工发送或构造 PDU、ICReq、H2C DATA、R2T、TERM REQ、digest 等协议内容。
- 写入结果前删除仍在步骤中出现的“开发协助”、“注入故障”、“使命令卡住”、“使 IO 不返回”、“手工恢复故障”、“触发或等待内部流程”等动作；它们要么属于自动前置条件，要么应转换为正常产品操作。
- 测试步骤和主要预期不得出现 qpair、queue、callback、内部资源对象、协议状态码或返回值位。把它们转换成连接是否成功、IO 是否完成或挂起、设备是否可用、服务是否存活以及能否恢复。
- 某一步预期进程或服务崩溃、退出或停止后，后续操作前必须显式写出重启并等待服务恢复；故障窗口恢复不会自动复活进程。
- 如果结论是某个产品公开动作不能恢复，正式步骤必须在故障终态实际执行该动作，并紧接公开
  重试或状态查询，用外部结果证明；不能只在流程说明或分析备注中声称“无法恢复”。
- 部分副作用已经释放引用或资源后，清理步骤不得再次执行同一释放操作；应重建或重启拥有该状态的进程。
- 前置条件限定 Debug 或 Release 构建后，只写该构建下唯一、可判定的预期；不要混入另一构建，也不要使用“可能”“A 或 B”。
- 本 Skill 只帮助生成用例，不新增标签、评分、校验、阻断或自动返工。
- 正常主干、业务分支、异常传播、并发、重试和恢复属于 `branch` 用例；只有真实 Coverage
  缺口驱动的补测使用 `coverage`，围绕已确认问题的验证使用 `risk`。同一用例只保存一份正文。
- 每条产品用例关联 `behavior-flow-v1` 中的具体路径。内部状态机的详细推演放在证据或分析说明，
  不复制到用例的 entry、steps、external_observations 和 cleanup。
- 并发或多参与者流程的节点要标出参与者；边只能表示该参与者的真实后继或明确的跨参与者同步，
  不能把 A 的完成节点写成 B 的结果。

## 判断问题

每一批写入前只做一次自查：不了解源码的测试人员，能否仅凭产品正常入口执行这些步骤，并从外部结果判断成功或失败？步骤之间是否矛盾或包含猜测？如果不能，继续向上转换操作层级并删掉猜测动作。

如果故障条件必须由开发预先配置，测试人员的执行仍应类似：

1. 在开发提供的故障环境下，通过主机正常入口连接或执行 IO。
2. 观察连接、IO、设备和服务状态。
3. 等待故障环境按预设窗口自动恢复后，重新连接或执行 IO，确认恢复。

不要写成“测试人员构造报文、发送协议字段、检查内部对象”。

## 示例

不推荐：

1. 调用 `nvmf_subsystem_set_keys` 把主机密钥更换为 `key1`。
2. 发送 `SEND(DHCHAP_REPLY)`，使目标端进入 `FAILURE1`。
3. 发送 `AUTHENTICATION_RECV` 并检查 `AUTH_failure1`。

推荐：

前置条件：目标端和主机均使用 `key0`，主机可以正常连接目标端。

1. 通过目标端正常配置入口把主机密钥更换为 `key1`。
2. 主机保持原来的 `key0`，重新连接目标端。

预期结果：主机认证失败，无法完成连接，也无法访问目标端提供的存储设备。

恢复：将主机密钥更新为 `key1`，重新连接并确认设备恢复可用。
