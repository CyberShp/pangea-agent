# 产品黑盒用例写法

生成顺序、完整范围、场景粒度、产物格式、分类与示例统一使用当前 task 实际提供的冻结规则：
behavior-test-v2 读取共同生成及当前场景 rubric，behavior-test-v1 读取 rubric_behavior_test_generation；
更早任务只用自己的合同。本 Skill 只补充用例表达，不读取未提供的旧/新规则，不引入审核或门禁。

1. **采用实际产品入口。** 步骤写本次资料已证实的 CLI、RPC、应用或配置操作；预期写
   最终响应、连接、设备、IO 或服务日志。内部函数调用、局部变量及内部状态推演放在源码依据中。
   FIN/RST、协议字段、抓包和已有注入手段可以是实际刺激或观测，保留执行需要的细节；不能因技术名词判为白盒。
   公开 C API 的直接调用属于接口测试，需要已提供的调用宿主、输入、观测与清理方法。
2. **保持前后状态一致。** 前置写第一步开始时的状态；本次配置变化写在步骤里。失败、
   断开、资源释放或进程退出后的下一步继承真实状态；需要重建、重启、重新注册时明确操作。
   清理处理本次创建的对象并恢复本次修改的配置，已经释放的对象不重复释放。
3. **使用实际已有的设施。** 本轮已有故障设施可用于前置、执行中的定点注入或清理；函数/变量仅用于说明注入位置，主要验收仍是业务结果，按
   rubric 标明真实测试层级。当前缺少故障设施、调用宿主或可控制的触发时机时，用 note
   写“分支行为、缺少的具体操作/设施、源码依据”；这是有效的执行缺口交付。
4. **短句表达一次场景。** 按当前冻结 rubric 确定业务或公开接口验证目标及拆合理由，
   不由本 Skill 追加按内部路径、函数或 if 拆例的要求。关联判断用于理解条件，不逐项转成操作和预期。
   共用命令、参数和完整测试数据集中写一份操作 note。每条用例只写必要的前置、实际动作、对应预期和清理。
   参数变体引用明确输入，各自采用确定的预期。
5. **区分对象与证据。** 连接名、设备名、密钥名分别用于自己的操作与查询。异步操作采用
   用户最终收到的响应；内部受理返回、回调和资源状态只用于核实依据。风险复现需要的产品
   恢复动作要实际列在步骤中，环境复位不写成产品自愈。
6. **如实填写用途和状态。** 普通主干、模式、异常和恢复用例使用 `purpose=branch`；有
   本次真实 Coverage 数据驱动才使用 `coverage`；已确认问题验证使用 `risk`。未执行保持
   `not_run`。用例与流程按冻结方法论关联，完整范围中有依据的执行缺口保留在 note/summary。

保存前按冻结方法论做一次就地核对：测试人员能否按当前状态执行，是否能从外部判定结果，
清理后能否开始下一条用例。示例采用冻结方法论中的短用例，实际结论仍由当前源码和资料决定。

仅按当前 task 冻结的 profile、analysis_scene、objective 与 rubric 执行比例目标：behavior-test-v1 沿用冻结的黑盒与可实施灰盒至少 70% 目标；behavior-test-v2 的 risk 场景及显式 interface-contract 目标豁免该比例，其余按冻结规则执行。缺少 objective 的旧任务保持原冻结口径，不从库/驱动名称推断目标。用例及变体的粒度和计数遵循当前冻结规则，旧 Run 不追补新版场景职责。需要新增桩点的设计如实注明设施待准备，不能改标签或虚构外部命令凑比例。
